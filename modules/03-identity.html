The mental map

Identity has a lot of product names, and they change every couple of years. (Azure AD became Microsoft Entra ID; B2C became External ID.) Don't memorise names in isolation. Memorise the journey every access request takes, and then hang each service on the step it belongs to.

Related

03.1

Identity is the new perimeter

Imagine this

The old model was a castle with a moat: once you crossed the drawbridge (VPN), you could wander anywhere inside. The new model is an airport. Your passport is checked at check-in, again at security, again at immigration, and your boarding pass is scanned at the gate. Being inside the airport earns you nothing on its own. Every door asks again.

That airport model has a name: Zero Trust. Three principles, and you'll see them behind almost every design choice in this module:

Verify explicitlyDecide on every request using all available signals: who, from where, on what device, with what risk.
Use least privilegeGive the smallest permission, at the smallest scope, for the shortest time.
Assume breachDesign as if an attacker is already inside: segment, encrypt, log and limit the blast radius.
Developer view

"Authentication is a login page. I'll store users in a table and hash the passwords."

Architect view

"Never build your own identity system. Delegate to a proper identity provider so we get MFA, risk detection, auditing and compliance for free, and we never hold a password we could leak."

03.2

Microsoft Entra ID

The cloud identity provider behind everything Microsoft

Definition

Microsoft Entra ID (formerly Azure Active Directory) is Microsoft's cloud-based identity and access management service. It authenticates users, devices and applications and issues tokens that Azure, Microsoft 365 and thousands of other applications trust.

In plain words

Entra ID is the passport office for your organisation. It keeps the list of who exists (users, groups, apps, devices), checks their credentials, and hands out short-lived passes (tokens) that other services accept.

Every Azure subscription trusts exactly one Entra tenant. A tenant is one instance of Entra ID: one organisation's directory, with its own users, its own domain names (meridian.com) and its own security settings. The tenant decision is one of those one-way doors from Module 01. Most organisations should have one workforce tenant and resist the urge to create more.

Entra ID is not cloud Active Directory

The old name caused years of confusion. Here's the difference, because the exam loves it:

Active Directory Domain Services (on-prem)Microsoft Entra ID
Designed forCorporate network, domain-joined PCs and serversInternet, SaaS apps, cloud resources, any device
ProtocolsKerberos, NTLM, LDAPOpenID Connect, OAuth 2.0, SAML
StructureForests, domains, OUs, Group PolicyFlat directory, groups, administrative units
Typical question"Can this PC join the domain?""Can this user, on this device, open this app now?"

If a lifted-and-shifted legacy app in Azure still needs Kerberos/LDAP and you don't want to run domain controllers yourself, the answer is Microsoft Entra Domain Services, a managed domain that syncs from Entra ID.

Editions: what you get at each level

EditionHeadline capabilitiesArchitect's rule of thumb
FreeUsers, groups, basic SSO, security defaults, hybrid syncFine for a lab, not for a company.
P1Conditional Access, dynamic groups, self-service password reset with on-prem writeback, application proxyThe real baseline for any business.
P2Everything in P1 plus Identity Protection (risk-based access), Privileged Identity Management, access reviewsNeeded when the question mentions risk, just-in-time or reviews.
Entra ID Governance add-onAdvanced lifecycle workflows, entitlement management and review featuresFor mature identity governance programmes.
Exam cue

Licensing hides inside "minimise cost" questions. If the requirement is only "require MFA for remote users", P1 (Conditional Access) is enough. If it says "based on sign-in risk" or "just-in-time admin access", you need P2.

  2. Users › All users › + New user › Create new user: UPN priya@your tenant domain, display name Priya Sharma, auto-generate the password (copy it). On Properties set Department = Online › Create.
  3. Groups › All groups › + New group: type Security, name grp-az305-checkout-devs, membership type Assigned, add Priya as a member › Create.

  • Assign access to groups, not individuals. Dynamic groups make joiner/mover/leaver automatic, but only if HR data like Department is accurate.
  • The Tenant ID is what every Azure subscription points to: one subscription, one trusted tenant.

Say: “This is the passport office. Everything later in this module just reads from it.”

03.3

Hybrid identity: one person, one identity

Definition

Hybrid identity is a common user identity for authentication and authorisation across on-premises and cloud resources, typically created by synchronising Active Directory to Entra ID with Microsoft Entra Connect Sync or Microsoft Entra Cloud Sync.

In plain words

Your staff already have AD accounts. You don't want them to have a second, separate cloud username and password. So you copy (sync) the accounts to Entra ID and choose how the cloud checks their password.

Three ways to check a hybrid user's password

Password hash synchronisation (PHS)A hash of the password hash is synced to Entra ID, which then authenticates in the cloud. Simplest, most resilient, enables leaked-credential detection.
Pass-through authentication (PTA)Entra ID forwards the password check to lightweight agents on-premises, which validate against AD in real time. No password hashes in the cloud.
Federation (AD FS)Entra ID redirects users to your own on-prem federation servers. Most control, most infrastructure, most ways to break.
The instinct

"Storing password hashes in the cloud feels risky. Let's federate so everything stays on-prem."

Architect view

"Federation means our AD FS farm becomes a tier-0 dependency for every cloud login. If it goes down, so does Microsoft 365 and the Azure portal. PHS gives us leaked-credential detection and survives an on-prem outage. Choose federation only for a requirement PHS can't meet."

Exam cue

"Minimise on-premises infrastructure" or "users must sign in even if the on-prem datacentre is unavailable" → PHS. "Enforce on-prem account policies (e.g. logon hours) at sign-in" → PTA. "Use an existing third-party MFA or smart card solution integrated with AD FS" → federation. For syncing from multiple disconnected AD forests with a light footprint, Cloud Sync is the modern choice.

Portal demoWhere hybrid identity shows up (no setup needed)~1 min

Goal: Show where the PHS, PTA or federation decision becomes visible, without building a lab.

  1. In the Entra admin centre search Microsoft Entra Connect (under hybrid management).
  2. Show the status page: Connect Sync vs Cloud Sync, last sync time, and the user sign-in section: password hash sync, pass-through authentication, seamless SSO and federation, each shown as enabled or disabled.
  3. If your tenant is synced, open a synced user: On-premises sync enabled = Yes, and most properties are read-only in the cloud.

Say: “The choice you make in the installer ends up on this one status page, so this is the first place to look when sign-ins break.”

03.4

External identities: partners and customers

Not everyone who needs access is your employee. AZ-305 cares about two very different outsiders: partners who help you work, and customers who buy from you. Mixing them up is a classic wrong answer.

Microsoft Entra B2B collaboration

Definition

B2B collaboration lets you invite external users into your workforce tenant as guests so they can access your apps and resources using their own identities, whether a work account, a personal Microsoft account or a one-time passcode.

Imagine this

A visiting consultant gets a visitor badge at reception. They still have their own company's ID card. You decide which floors the visitor badge opens; their company decides whether they're still employed. If they leave their company, their home account dies, and with it their ability to use your visitor badge.

  • Cross-tenant access settings let you trust a partner's MFA and device compliance, so guests aren't asked for MFA twice.
  • B2B direct connect is a lighter variant used mainly for Teams shared channels, with no guest object in your tenant.
  • Guests are a governance risk over time, so pair them with access reviews.

Microsoft Entra External ID for customers (formerly Azure AD B2C)

Definition

Microsoft Entra External ID in an external tenant is a customer identity and access management (CIAM) solution that lets consumers and business customers sign up and sign in to your apps with email, social or enterprise identities, using fully branded experiences.

In plain words

It's a ready-made "Sign up / Sign in with Google" system for your customer-facing apps, built for millions of users, so your developers never write a password table again.

Name check

Many exam questions and older documents still say Azure AD B2C. Since May 2025, Azure AD B2C is no longer available to new customers, and Microsoft directs new customer-identity projects to External ID. Existing B2C tenants remain supported. In an exam answer, "B2C" and "External ID for customers" solve the same problem: customer sign-up and sign-in.

ScenarioChoose
Supplier staff need access to your SharePoint and an internal appB2B collaboration (guests in your workforce tenant)
Shoppers create accounts on your e-commerce site with Google or emailExternal ID for customers (Azure AD B2C in older questions)
Two companies' employees chat in a shared Teams channelB2B direct connect
A legacy app in Azure VMs needs LDAP/Kerberos for staffEntra Domain Services (not an external identity at all)
Portal demoInvite a partner, then peek at an external tenant~3 min

Goal: Make the difference between a visitor badge (B2B) and a customer loyalty card (External ID) concrete.

  1. Users › All users › + New user › Invite external user: use a personal email you own › Invite. In the user list, User type = Guest.
  2. Open the invitation email on your phone and accept. The consent screen names the organisation you're joining and what it can see.
  3. External Identities › External collaboration settings: who may invite guests, and how restricted guest access is.
  4. External Identities › Cross-tenant access settings › Default settings › inbound Trust settings: the option to trust MFA from other Entra tenants.
  5. Overview › Manage tenants › + Create: show the choice between Workforce and External (for customers). Cancel.

Point out while you are there

  • Partners come into your workforce tenant as guests. Customers live in a separate external tenant.

Say: “A visitor badge for partners, a loyalty card for customers. Never mix the two in one tenant.”

Clean up: Delete the guest user at the end of the module.

03.5

Strong authentication: MFA and passwordless

Passwords alone are no longer enough. Microsoft's own data has long shown that MFA blocks the overwhelming majority of account-compromise attacks. Microsoft now requires MFA for signing in to the Azure portal, admin centres and Azure management tools, so treat MFA as the floor, not a feature.

MFASomething you know plus something you have (phone, key) or are (biometric).
Passwordless & phishing-resistantPasskeys (FIDO2 security keys or the Authenticator app), Windows Hello for Business, certificate-based auth. No password to steal.
Self-service password reset (SSPR)Users reset their own passwords after verifying themselves. With P1 it can write back to on-prem AD.
Security defaultsA free, one-switch baseline: MFA registration for all, MFA for admins, legacy auth blocked. Good for small tenants. Replace with Conditional Access when you need nuance.
Exam cue

"Small organisation, no premium licences, enable MFA quickly" → security defaults. "MFA only outside the office" or "only for this app" → Conditional Access (P1). "Phishing-resistant" → passkeys/FIDO2 or Windows Hello for Business, enforced with an authentication strength in Conditional Access.

Portal demoSecurity defaults and authentication methods~2 min

Goal: Show the one-switch baseline and where passwordless methods are switched on.

  1. Overview › Properties › Manage security defaults: show the panel. Don't toggle it if Conditional Access policies exist; the two are mutually exclusive.
  2. Authentication methods › Policies: Passkey (FIDO2), Microsoft Authenticator, Temporary Access Pass, SMS… Open Passkey and show how to target it at a group.
  3. Authentication methods › Authentication strengths: open the built-in Phishing-resistant MFA strength. Conditional Access can require exactly this.
  4. Users › Priya › Authentication methods: what she has registered, plus Require re-register MFA.

Say: “Security defaults are a light switch. Conditional Access is a dimmer with a timer. Small tenants start with the switch.”

03.6

Conditional Access

The Zero Trust policy engine

Definition

Conditional Access is the Entra ID policy engine that brings signals together (user, location, device, application and risk) to decide whether to allow access, block it, or allow it only after extra requirements such as MFA or a compliant device.

In plain words

It's a set of if-then rules evaluated after the password is checked. If a finance user opens the payroll app from an unknown country on a personal laptop, then block. If the same user is on a company laptop in the office, then let them straight in.

Policies almost every organisation should have

  • Require MFA for all users, with phishing-resistant methods for admins.
  • Block legacy authentication protocols that can't do MFA.
  • Require a compliant device for access to sensitive apps.
  • Block or step up access from countries you don't operate in.
  • Require MFA for Azure management (portal, CLI, PowerShell).
Common trap

A badly scoped "block everything" policy can lock out every administrator, including you. Always keep two emergency access ("break-glass") accounts excluded from policies (and monitored with alerts), and test new policies in report-only mode before switching them on.

Portal demoBuild a policy in report-only and test it with What If~5 min

Goal: Build an if-then policy live and show the safe rollout pattern: report-only first, What If to test.

Before you start: Scope the policy to the demo group only and exclude your own admin account. A typo with “All users” can lock you out.

  1. Protection › Conditional Access › Policies. Show Create new policy from templates (e.g. “Require MFA for admins”), then go back and choose + New policy.
  2. Name: DEMO – Require MFA for Azure management. Users: include grp-az305-checkout-devs; exclude your admin account.
  3. Target resources › Select resources › search for Azure management (it may be listed as Windows Azure Service Management API).
  4. Conditions: briefly open Locations, Device platforms and Sign-in risk so learners see the signals from the diagram.
  5. Grant › Grant access › tick Require multifactor authentication (or Require authentication strength).
  6. Enable policy › Report-only › Create.
  7. Policies › What If: user Priya, target Azure management › What If. The policy is listed as one that would apply.
  8. Later: Sign-in logs › open one of Priya's sign-ins › Report-only tab shows what the policy would have done.

Point out while you are there

  • Report-only → check logs → On. Always.
  • Keep two break-glass accounts excluded and monitored.

Say: “Signals in, decision out. And we test in report-only, because a wrong policy locks out a whole company, admins included.”

Clean up: Delete the demo policy.

03.7

Identity Protection

Definition

Microsoft Entra ID Protection uses machine learning and threat intelligence to detect identity-based risks, such as leaked credentials, sign-ins from anonymous IP addresses or unfamiliar locations, and calculates a sign-in risk and a user risk that can drive Conditional Access decisions.

Imagine this

Your bank texts you: "A card payment of ₹80,000 was attempted in another country one hour after you used it in Pune. Was this you?" The bank didn't block your card forever. It noticed something odd and asked for proof. That's exactly what Identity Protection does for sign-ins.

Sign-in risk

"Is this sign-in probably not the real owner?" Anonymous IP, atypical travel, unfamiliar sign-in properties. Typical response: require MFA.

User risk

"Is this account probably compromised?" Leaked credentials found online, unusual behaviour. Typical response: require a secure password change.

Identity Protection needs Entra ID P2. Its risk levels feed into Conditional Access as conditions, which is the modern way to configure risk-based policies.

Hybrid connection

The leaked credentials detection for synced users works only if you use password hash sync, because Microsoft needs a hash to compare against leaked lists. One more reason PHS is the recommended default.

Portal demoOpen the risk dashboards~2 min

Goal: Show where risk is detected and how it feeds Conditional Access.

  1. Protection › Identity Protection › Dashboard: risky users, risky sign-ins, risk detections.
  2. Risky sign-ins › open one if any exist. To create a detection on purpose, sign in as Priya from the Tor Browser (anonymous IP); it appears after a few minutes.
  3. On a risky user, show the admin actions: Confirm user compromised, Dismiss user risk, Reset password.
  4. Go back to a Conditional Access policy › Conditions › User risk / Sign-in risk: this is where risk-based policies are built now.

Say: “It's your bank's ‘was this you?’ text message, for every sign-in, and it needs P2.”

03.8

Authorisation with Azure RBAC

Definition

Azure role-based access control (RBAC) is the authorisation system for Azure resources. Access is granted by creating a role assignment, which binds a security principal to a role definition at a scope.

The four fundamental built-in roles

RoleCan manage resources?Can grant access to others?Typical holder
OwnerYes, everythingYesPlatform team, at limited scopes, ideally via PIM
ContributorYes, everythingNoWorkload team on their own resource groups
ReaderNo, view onlyNoAuditors, support, finance
User Access AdministratorNoYesIdentity/security team

Beyond these, there are hundreds of service-specific roles (Virtual Machine Contributor, Key Vault Secrets User, Storage Blob Data Reader…). The newer Role Based Access Control Administrator role can grant access too, but can be constrained with conditions to only assign specific roles, a safer alternative to handing out Owner.

Two distinctions the exam loves

Control plane vs data plane

Contributor on a storage account lets you manage the account (settings, firewall). Reading the blobs with Entra ID needs a data role like Storage Blob Data Reader. Managing the box is not the same as opening it.

Entra roles vs Azure roles

Entra roles (Global Administrator, User Administrator) manage the directory: users, groups, licences. Azure roles (Owner, Contributor) manage Azure resources. A Global Admin has no Azure resource rights by default, though they can elevate themselves.

Developer view

"Just give me Owner on the subscription so I'm not blocked."

Architect view

"Assign roles to groups, not individuals. Use the narrowest built-in role at the narrowest scope. Create a custom role only when no built-in role fits. Make standing privileged access rare, and use PIM for the rest."

Exam cue

"Least privilege" plus a very specific task (e.g. "restart VMs but not delete them") → a custom role if no built-in role matches exactly. Check built-ins first, though: Virtual Machine Contributor, for instance, also allows deleting VMs. The exam often tests whether you notice that.

Portal demoGive a group Reader on a resource group, then check it~3 min

Goal: Build “who + what + where” live and show control-plane vs data-plane roles.

  1. Azure portal › Resource groups › create rg-az305-m03-demo (Central India) › open it › Access control (IAM).
  2. + Add › Add role assignment: show the Job function roles and Privileged administrator roles tabs. The portal deliberately separates the dangerous ones. Pick Reader.
  3. Members › + Select members › grp-az305-checkout-devs › Review + assign. Who = group, what = Reader, where = this resource group.
  4. Check access › search Priya: Reader at this scope, granted via the group.
  5. Role assignments tab: the Scope column shows which assignments are inherited from the subscription or a management group.
  6. Roles › open Storage Blob Data Reader › permissions: DataActions, not Actions. That's the data plane.

Say: “Every access sentence needs three parts: who, what and where. If one is missing, it isn't an access design.”

03.9

Privileged Identity Management (PIM)

Definition

Microsoft Entra Privileged Identity Management provides just-in-time, time-bound and approval-based activation of privileged Entra roles, Azure roles and group memberships, with full auditing.

Imagine this

A bank manager doesn't carry the vault key in their pocket all day. When they need the vault, they sign the register, a second officer approves, they get the key for 30 minutes, and it goes back in the safe. PIM is that register, that approval and that timer, for admin rights.

Exam cue

"Just-in-time", "time-bound", "require approval to activate", "minimise the number of permanent administrators" → PIM (Entra ID P2 or ID Governance).

Portal demoMake Priya eligible, then activate just-in-time~4 min

Goal: Show standing access turning into temporary, approved, audited access.

Before you start: Needs Entra ID P2 (or ID Governance) and the RBAC demo's resource group.

  1. Search Privileged Identity Management › Azure resources › select rg-az305-m03-demo (choose Manage resource if asked).
  2. Settings › Contributor › Edit: activation maximum 2 hours, require justification, require MFA on activation, require approval (approver: you) › Update.
  3. Assignments › + Add assignments: role Contributor, member Priya › Next › assignment type Eligible › Assign.
  4. In a private window, sign in as Priya › search Privileged Identity Management › My roles › Azure resources › Activate, with a justification › submit.
  5. As yourself: PIM › Approve requests › approve. Priya now shows an active assignment with an end time.
  6. Show the Resource audit log: who requested, who approved, when it expires.

03.10

Access reviews: fighting permission creep

Definition

Access reviews let organisations efficiently manage group memberships, access to applications and role assignments by having reviewers regularly confirm that each user still needs their access, with optional automatic removal when access is not confirmed.

In plain words

People change teams, projects end, contractors leave, and nobody remembers to remove their access. Access reviews are a recurring "is this still needed? yes/no" email to the person who should know, plus automatic clean-up for every "no" or non-response.

  • Review guest users every quarter: the classic use case.
  • Review privileged role assignments (works together with PIM).
  • Reviewers can be managers, group owners, the users themselves, or specific people.
  • Pair with entitlement management access packages so access is requested, approved and time-limited from the start.
Exam cue

"Auditors require quarterly attestation of who has access", "remove guest users who no longer need access", "minimise administrative effort to review group membership" → access reviews.

Portal demoSchedule a quarterly guest access review~2 min

Goal: Show how “auditors want quarterly attestation” becomes a scheduled, self-cleaning process.

  1. Search Identity Governance › Access reviews › + New access review.
  2. Review type: Teams + Groups, scope Guest users only, group grp-az305-checkout-devs (add your guest to it first if you like).
  3. Reviewers: Group owner(s), with yourself as fallback reviewer.
  4. Settings: recurrence Quarterly, Auto apply results on, and if reviewers don't respond: Remove access › Create.

Point out while you are there

  • “No response = remove” is the audit-friendly default. Silence should never keep access alive.

Clean up: Delete the access review.

03.11

Identities for applications

Humans are only half the story. Your web app needs to read from a database, your function needs to drop a message in a queue, your pipeline needs to deploy. Each of those is a non-human identity, and they're where most leaked credentials come from.

App registrationThe global definition of an application in Entra ID: its ID, redirect URIs and permissions. Think of it as the blueprint.
Service principalThe local instance of that app in a tenant: the identity that actually signs in and gets roles. Think of it as the employee badge.
Managed identityA service principal that Azure creates and manages for you, with credentials you never see, rotate or store.
Workload identity federationLets external systems (GitHub Actions, Kubernetes, other clouds) exchange their tokens for Entra tokens, with no secret stored anywhere.

Managed identities

Definition

Managed identities provide Azure resources with an automatically managed identity in Microsoft Entra ID, which they can use to obtain tokens for any service that supports Entra authentication, without any credentials in code or configuration.

Imagine this

Instead of giving the delivery driver a copy of your house key (a secret they could lose or copy), you register their face with the society security guard. The guard (Entra ID) recognises them each time and lets them in for that delivery. There's no key to leak.

System-assignedUser-assigned
CreatedAs part of a resource (switch it on)As its own standalone Azure resource
LifecycleDeleted with the resourceIndependent; survives resource deletion
SharingOne resource onlyCan be attached to many resources
Best forOne app, one identity, simpleMany instances needing the same access (scale sets, blue/green), or pre-granting access before the resource exists
Exam cue

"Without storing credentials", "minimise secret management", "app must access Storage/SQL/Key Vault securely" → managed identity. "Multiple VMs/apps share the same permissions" or "identity must persist when the resource is recreated" → user-assigned. "Pipeline outside Azure (e.g. GitHub Actions) without secrets" → workload identity federation.

Portal demoGive a web app an identity and a role: no secret anywhere~5 min

Goal: Show the managed identity flow from the diagram: the app gets an identity, the identity gets a role, and nobody copies a key.

  1. App Services › + Create › Web App: name app-az305-m03 plus your initials, any runtime, region Central India, pricing plan Free F1 (or Basic) › Review + create › Create.
  2. Open the web app › Settings › Identity › System assigned › Status On › Save. Copy the Object (principal) ID.
  3. In Entra › Enterprise applications, filter Application type = Managed Identities: the app now exists in the directory.
  4. Open a storage account (create one in the resource group if needed) › Access control (IAM) › Add role assignment › Storage Blob Data Reader › assign access to Managed identity › + Select members › App Service › your app › Review + assign.
  5. Contrast: storage account › Security + networking › Access keys. This is what developers used to paste into config files. We didn't need it.
  6. Optional: search Managed Identities › + Create a user-assigned identity, then attach it under the web app's Identity › User assigned tab.

Point out while you are there

  • System-assigned dies with the app. User-assigned lives on its own and can be shared.
  • Next level: in the storage account's Configuration, set Allow storage account key access to Disabled, so only Entra identities work.

Say: “We didn't give the driver a key. We registered him with the security guard.”

03.12

Azure Key Vault

A safe for secrets, keys and certificates

Definition

Azure Key Vault is a cloud service for securely storing and controlling access to secrets (passwords, connection strings), cryptographic keys and TLS/SSL certificates, with access controlled by Entra ID and every operation logged.

Imagine this

Key Vault is the bank locker. You don't keep jewellery under your mattress (in code or config files). You keep it in a locker where every visit is recorded, only named people can open it, and the bank keeps it safe if your house burns down.

SecretsAny small sensitive string: connection strings, API keys, passwords.
KeysCryptographic keys used for encryption and signing, including customer-managed keys for storage and databases.
CertificatesTLS certificates with lifecycle management and auto-renewal from supported CAs.

Choosing the tier

OptionKey protectionChoose when
Key Vault StandardSoftware-protected keysSecrets and certificates for most apps.

Design decisions an architect makes

  • Permission model: use Azure RBAC (e.g. Key Vault Secrets User, Key Vault Crypto Officer). The older access policies model is still supported but is less granular and doesn't fit PIM.
  • One vault per application, per environment, per region. This limits the blast radius and avoids throttling, and dev can never read prod secrets.
  • Soft delete is always on (7–90 days retention). Turn on purge protection for production, so even an admin can't permanently delete keys during the retention period. This is required when keys encrypt other services (customer-managed keys).
  • Network: disable public access and use a private endpoint for sensitive workloads.
  • Rotation: configure automatic key rotation and certificate auto-renewal; send expiry events to Event Grid.
  • Logging: send diagnostic logs to Log Analytics so every secret read is auditable (see Module 04).
Developer view

"I'll put the connection string in appsettings.json and mark the repo private."

Architect view

"Best: no secret at all, because the app uses its managed identity to reach SQL directly. Next best: the secret lives in Key Vault, the app reads it with its managed identity, App Service uses a Key Vault reference, and rotation never needs a redeploy."

Exam cue

"Protect against accidental or malicious deletion of keys" → soft delete + purge protection. "Keys must be stored in a FIPS 140 Level 3 HSM" → Premium or Managed HSM ("single-tenant" or "full control" → Managed HSM). "Centrally store app secrets and audit access" → Key Vault with diagnostic logging.

03.14

Recap and self-check

Architect's identity checklist

  • One workforce tenant; customers in a separate external tenant.
  • Hybrid users synced, with PHS on (even as a backup).
  • MFA everywhere, phishing-resistant for admins, legacy auth blocked.
  • Two monitored break-glass accounts excluded from Conditional Access.
  • Roles assigned to groups, at the narrowest scope, with privileged roles in PIM.
  • Recurring access reviews for guests and privileged roles.
  • Apps use managed identities; Key Vault holds whatever secrets remain.

Self-check

1. Users must keep signing in to Microsoft 365 even if the on-premises datacentre is offline. Which hybrid authentication method?

Password hash synchronisation. Authentication happens entirely in Entra ID, so on-prem availability doesn't matter. PTA and federation both depend on on-prem components.

2. Customers of a mobile app must sign up with their Google or Apple accounts. What do you recommend?

Microsoft Entra External ID for customers in an external tenant (Azure AD B2C in older questions). B2B is for partners, not consumers.

3. Require MFA only when a user's sign-in is considered medium or high risk. What do you need?

Identity Protection sign-in risk used as a condition in a Conditional Access policy, which requires Entra ID P2.

4. Five VMs in a scale set and two Function apps need identical access to a storage account. Which identity type, and why?

A single user-assigned managed identity attached to all of them, with one role assignment (e.g. Storage Blob Data Contributor). This means one place to manage the permission, and it survives instances being recreated.

5. A Global Administrator can't see any subscriptions in the Azure portal. Why?

Global Administrator is an Entra role (directory), not an Azure role. They have no Azure RBAC assignments by default. They can elevate to User Access Administrator at the root scope, but that should be temporary and audited.

6. Keys in Key Vault must not be permanently deletable, even by an administrator, for 90 days. Configuration?

Soft delete with 90-day retention plus purge protection. With purge protection on, deleted items can't be purged until retention expires.

Carry this into Module 04

We've decided who gets in and what they can do. But how do we know what actually happened: who signed in, which secret was read, which VM is struggling? Without monitoring, every control in this module is a promise you can't verify.
