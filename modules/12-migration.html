Module 12

Migration: Moving House Without Losing the Furniture

"Move everything to Azure in 18 months" sounds like one project. It's really six hundred small decisions: which server moves as it is, which one gets rebuilt, which one should simply be switched off. Get the order wrong and you migrate a database before the app that needs it to be next door. This module is the method: understand the estate, choose a strategy per workload, then move in waves with the right tool for each piece.

The mental map

Every migration runs the same loop: discover what you have, assess where each piece should go and what it will cost, migrate it with the right tool, then optimise and hand it over to operations. Around the loop sit the Cloud Adoption Framework (the method) and the landing zone (the destination you built in Parts I–IV).

12.1

Why migrations fail

Imagine this

Moving house from Bengaluru to Hyderabad. If you throw everything into a truck the night before, you pay to move the broken cooler, the kitchen arrives three days after the family, and the new flat has no gas connection. Good movers do it differently: walk the house and make a list, decide what to sell, what to carry and what to buy new, book the new flat's connections first, then move room by room. That's a migration plan.

No inventory"We think there are about 400 servers." There are 600, and 40 nobody owns.
Hidden dependenciesThe app moves to Azure; its database stays behind; every query now crosses a WAN link and the app crawls.
No landing zoneVMs arrive in a subscription with no network plan, no policies and no backup. Fixing it later is a second migration.
Lift-and-shift of oversized VMsA 16-core server at 5% CPU, moved as-is, costs more in Azure than it did on-premises.
Big bangEverything over one weekend, no rehearsal, no rollback plan.
Developer view

"Let's just replicate all the VMs and switch over. We can modernise later."

Architect view

"Rehosting is often right, to hit a datacentre exit date. But it's a decision per workload, made with data: dependencies, right-sizing, licences, cost. And we decide what we'll never move: 10–20% of most estates can be retired."

Mindset takeaway

A migration is a business project with a technical part. Start from the motivation (datacentre lease ending, cost, agility, security) and let it decide speed versus modernisation for each workload.

12.2

The Cloud Adoption Framework

The method behind the move

Definition

The Microsoft Cloud Adoption Framework for Azure (CAF) is a collection of documentation, guidance, best practices and tools to help organisations adopt the cloud. It is organised into methodologies: Strategy, Plan, Ready, Adopt (migrate, modernise, innovate), Govern, Secure and Manage.

Exam cue

"Business justification, motivations" → Strategy. "Digital estate inventory, skills plan" → Plan. "Prepare the environment, landing zone" → Ready. "Move workloads" → Adopt. "Guidance and best practices for adopting the cloud" → the Cloud Adoption Framework (not the Well-Architected Framework, which is about designing individual workloads).

Portal demoFind the CAF tools: the strategy and readiness assessments~2 min

Goal: Show that CAF is more than documents: it has assessments and templates you can use with a customer.

  1. Browse to learn.microsoft.com/azure/cloud-adoption-framework: point at the methodology tiles (Strategy, Plan, Ready, Adopt, Govern, Secure, Manage).
  2. Open the Tools and templates page: the strategy and plan templates, and the Cloud Adoption Strategy Evaluator and Governance benchmark assessments in Microsoft Assessments.
  3. Back in the Azure portal, search Azure landing zones (or the landing-zone accelerator): the Ready step you built the pieces of in Modules 02–11.

Say: “The framework is the moving company's checklist. You've already done Ready, Govern, Secure and Manage; this module is Plan and Adopt.”

12.3

Choosing a strategy: the Rs

Each workload gets one strategy. The names vary between sources (you'll see "5 Rs", "6 Rs", "7 Rs"), but the dial is always the same: how much do we change it on the way?

StrategyWhat it meansAzure examplePick it when
RetireSwitch it off—Nobody uses it, or another system already does the job
RetainLeave it where it is, for nowManage with Azure ArcMainframe, hardware ties, regulation, or no business case yet
Rehost ("lift and shift")Move as-is to IaaSVMware VM → Azure VM with Azure MigrateDeadline-driven (datacentre exit), little or no code change possible
Replatform ("lift and optimise")Small changes to use a managed platformSQL Server → SQL Managed Instance; .NET app → App ServiceQuick wins: less patching and better HA with minimal code change
RefactorChange the code to fit cloud servicesMove sessions to Redis, files to Blob, containeriseThe app works but needs to scale or deploy faster
RearchitectChange the structureMonolith → microservices on Container Apps with Service BusThe architecture itself blocks scale, resilience or speed
RebuildRewrite cloud-native from scratchNew serverless app on Functions and Cosmos DBThe old app can't be saved, and it's a business differentiator
ReplaceBuy SaaS insteadOn-prem Exchange → Microsoft 365; CRM → Dynamics 365It's a commodity; no advantage in running it yourself
Imagine this

Moving house again. Retire: sell the old cooler. Rehost: carry the sofa as it is. Replatform: carry the sofa but get new covers that fit the new room. Refactor/rearchitect: turn the old wardrobe into built-in shelves. Rebuild: get a carpenter to make new furniture. Replace: the new flat comes furnished, so you just use theirs.

Exam cue

"Minimal changes", "as quickly as possible", "datacentre lease expires" → rehost. "Reduce management of SQL Server with minimal code changes" → replatform to SQL Managed Instance. "Use SaaS" → replace. "Application no longer needed" → retire.

12.4

Discover and assess with Azure Migrate

The surveyor before the movers

Definition

Azure Migrate is Microsoft's central hub for moving workloads to Azure. A small appliance discovers your servers (VMware, Hyper-V, physical, other clouds), databases and web apps, measures how busy they are and maps their dependencies. Assessments then recommend right-sized Azure targets with costs, and a business case compares on-premises and Azure total cost of ownership.

In plain words

You install one small VM (the appliance) in your datacentre. For a few weeks it quietly watches every server: what's installed, how busy it really is, and who it talks to. Then Azure Migrate tells you, per server, "this one fits a D4s_v5 at ₹X a month, this SQL database fits Managed Instance, these five servers always talk to each other so move them together", and builds the cost comparison your CFO will ask for.

Facts worth remembering

  • Two sizing modes: performance-based (uses collected utilisation; collect for at least a week, ideally a month, covering month-end peaks) and as on-premises (matches the current allocation).
  • No appliance yet? Import a CSV or RVTools export to get quick assessments.
  • Agentless dependency analysis works from the appliance; agent-based uses the Azure Monitor agent and the Dependency agent.
  • Assessments apply Azure Hybrid Benefit, reservations and savings plans if you tell them to (Module 09).
  • Azure Migrate also integrates partner tools (ISVs) for discovery and migration.
Exam cue

"Discover on-premises servers", "assess readiness", "right-size", "estimate cost of running in Azure" → Azure Migrate (discovery and assessment). "Identify dependencies between servers" → dependency analysis. "Compare TCO" → Azure Migrate business case (or the TCO Calculator for a quick estimate).

  2. In the project › Discover: point at the choices: Using appliance for VMware, Hyper-V, or physical/other clouds; and Import using CSV or RVTools. For the appliance, show the steps (generate project key, download OVA/VHD or installer). Don't download.
  3. Point at the project's tiles: Discovery and assessment, Migration and modernization, and where partner tools appear.

12.5

Migrating servers

Replicate, test, cut over

Definition

The Migration and modernization tool in Azure Migrate replicates servers to Azure and migrates them with minimal downtime. VMware and Hyper-V VMs can be migrated agentless; physical servers, other clouds and some VMware scenarios use agent-based replication through a replication appliance. Each server can be test-migrated into an isolated network before the final migration (cut-over).

  1. Replicate: initial copy of the disks, then continuous delta replication. Production keeps running.
  2. Test migrate: spin up a copy in an isolated VNet; the app team tests it. Repeat as often as needed. Clean up.
  3. Migrate (cut-over): in a maintenance window, stop the source (optional, recommended), do a final sync, start the Azure VM.
  4. Post-migration: switch DNS and routes, enable backup and monitoring, decommission the source after a safe period.
Name check

You may meet the older name Azure Migrate: Server Migration. Under the hood it shares technology with Azure Site Recovery (Module 08): replication and test failover are the same idea, used once for a move instead of forever for DR.

Common trap

Migrating servers one at a time without using the dependency map. Group servers that talk to each other into the same wave, or the latency between Azure and the datacentre will make the first wave look like a failure.

Exam cue

"Migrate VMware / Hyper-V VMs to Azure with minimal downtime", "agentless" → Azure Migrate: Migration and modernization. "Validate before cut-over without impacting production" → test migration. "Migrate physical servers or VMs from another cloud" → agent-based migration. "IIS / .NET web apps to PaaS" → Azure Migrate web app migration to App Service.

Portal demoWalk the replicate wizard and find test migration~3 min

Goal: Show replicate, test migrate and migrate as three separate, safe steps.

  1. Project › Migration and modernization › Replicate: show What do you want to migrate? (Servers or virtual machines), Are your machines virtualised? (VMware vSphere, Hyper-V, physical or other). Agentless needs a discovered VMware or Hyper-V estate; agent-based needs a replication appliance.
  2. Read the wizard's tabs aloud: source, virtual machines, target settings (subscription, VNet, availability zone or set), compute (size, OS disk, Hybrid Benefit), disks, tags. Cancel.
  3. Point at the Replicating machines list and its actions per machine: Test migration, Clean up test migration, Migrate (with the option to shut down the source first).

Say: “Copy the house while you still live in it, rehearse the move, then move on a quiet weekend.”

12.6

Migrating databases

Online or offline, that's the question

Definition

Azure Database Migration Service (DMS) is a fully managed service for migrating databases from multiple sources to Azure data platforms with minimal downtime. For SQL Server it supports migrations to Azure SQL Database, Azure SQL Managed Instance and SQL Server on Azure VMs, in offline mode (downtime for the whole copy) or online mode (continuous sync, short cut-over), driven from the Azure portal, PowerShell or the CLI.

Offline migration

Stop the app, back up, copy, restore, start the app in Azure. Downtime = the whole copy. Simple and fine for small databases or generous maintenance windows.

Online migration

Copy a full backup while the source keeps running, then keep applying changes (log backups or change capture). Cut over in minutes when you're ready. Needed when downtime must be short.

From → toTypical tool
SQL Server → SQL Managed InstanceDMS (online or offline), Managed Instance link (keeps a live, continuously synced copy on MI using distributed availability groups; you switch over in minutes), Log Replay Service (restores your existing full and log backups continuously until cut-over), or native backup/restore from URL
SQL Server → Azure SQL DatabaseDMS (offline), or transactional replication / data sync patterns for minimal downtime
SQL Server → SQL Server on Azure VMDMS, backup/restore, or rehost the whole VM with Azure Migrate
MySQL / PostgreSQL → Azure Database for MySQL / PostgreSQL flexible serverDMS or the built-in migration service in flexible server (online or offline)
MongoDB / Cassandra → Cosmos DBDMS or native tools; Data Factory for bulk copies
Name check

The Data Migration Assistant was retired in July 2025, and Azure Data Studio (with its Azure SQL migration extension) in February 2026. SQL Server assessment now happens in Azure Migrate or the SQL Server migration experience in Azure Arc, and migrations run from Database Migration Service in the portal. Older questions may still mention the retired tools; the decision logic (compatibility check first, then online vs offline) hasn't changed.

Exam cue

"Migrate SQL Server with minimal downtime" → DMS online (or MI link for Managed Instance). "Near 100% compatibility, SQL Agent, cross-database queries, minimal code change" → target SQL Managed Instance (Module 06). "Check compatibility issues before migrating" → Azure Migrate SQL assessment.

Portal demoSee online vs offline on the Database Migration Service screens~3 min

Goal: Show where a SQL migration is set up and the one decision that matters most: downtime.

  1. Search Azure Database Migration Services › + Create: source SQL Server, target Azure SQL Managed Instance (or SQL Database / SQL Server on Azure VM), migration service Database Migration Service. Walk the form, then cancel.
  2. Open any SQL Managed Instance (or its create form) and point at Migrations / Managed Instance link: the near-zero-downtime option.
  3. Search Azure Migrate › project › Discover: SQL Server instances discovered by the appliance get their own Azure SQL assessment with readiness and target recommendations.

Say: “Offline is closing the shop for the whole move. Online keeps it open until the last ten minutes.”

12.7

Moving data: online or offline

Sometimes a truck beats the internet

Before choosing a tool, do one sum: data size ÷ usable bandwidth. 200 TB over a 1 Gbps link at 80% usage takes about 23 days, if nothing else uses the link. If the answer is weeks, ship disks.

ScenarioTool
A few TB, good network, one timeAzCopy (scriptable) or Storage Explorer (GUI)
Many file shares to Azure Files or Blob, with a managed project and agentsAzure Storage Mover
Keep file servers on-premises but backed by Azure FilesAzure File Sync with cloud tiering
Tens of TB, slow or busy networkData Box Disk
Hundreds of TB, or no usable networkData Box
Ongoing transfers on a schedule, with transformationAzure Data Factory
Exam cue

"Limited bandwidth", "hundreds of TB", "no network connectivity", "ship" → Data Box family (Data Box Disk for smaller amounts). "Copy files with a command-line tool" → AzCopy. "Migrate file shares (SMB/NFS) as a managed project" → Storage Mover. "Keep a local cache of Azure Files on-premises" → File Sync.

Portal demoSize a Data Box order, then cancel before it ships~3 min

Goal: Show the offline transfer family and how the portal picks a device by data size.

  1. Search Azure Data Box › + Create: transfer type Import to Azure, source country India, destination region Central India › Apply.
  2. The product picker shows the options with capacity and price: Data Box Disk, Data Box (and larger models where offered), Import/Export. Read the capacities aloud.
  3. Select Data Box › walk the order tabs: destination storage account, encryption (customer-managed key option), shipping and contact details. Cancel on the last tab.

Point out while you are there

  • Do the sum first: data size ÷ usable bandwidth. If the answer is weeks, the truck wins.

Say: “Sometimes the fastest network in the world is a courier van.”

Portal demoCompare Storage Mover and AzCopy for online transfers~3 min

Goal: Show a managed file-share migration project next to the classic command-line copy.

  1. Search Storage movers › + Create: a Storage Mover resource in Central India. Point at the model: agents (VMs you run on-premises) → projects → job definitions (source SMB/NFS share → target Azure Files or Blob container). Cancel or create.
  2. Open any storage account › Storage browser: upload a file (the GUI way). Then Shared access signature › generate a short-lived SAS and show the AzCopy pattern: azcopy copy "D:\shares\finance" "https://<account>.blob.core.windows.net/finance?<SAS>" --recursive.

Say: “AzCopy is a moving van you drive yourself. Storage Mover is a moving company with a project plan.”

12.8

What stays: Azure Arc and VMware

Azure Arc

Definition

Azure Arc extends Azure management and services to resources outside Azure. It projects on-premises and other-cloud servers, Kubernetes clusters and SQL Server instances into Azure Resource Manager, so you can apply Azure Policy, RBAC, tags, Defender for Cloud, Azure Monitor and Update Manager to them as if they were Azure resources.

In plain words

Some servers will never move: the store servers, the factory controller, the mainframe neighbour. Arc gives each of them an Azure "ID card", so the same policies, patching, monitoring and security you built in Parts I–IV reach them too. One control plane, wherever the server lives.

Azure VMware Solution

Definition

Azure VMware Solution (AVS) provides private clouds running VMware vSphere, vSAN and NSX on dedicated bare-metal Azure hosts, managed by Microsoft. Workloads move with VMware HCX without re-platforming, and can use Azure services alongside.

Pick AVS when the requirement is "keep using VMware tools and skills", "move the whole VMware estate fast without converting VMs", or a datacentre exit date that leaves no time to re-platform.

Exam cue

"Manage on-premises / multicloud servers with Azure Policy, Defender, Monitor" → Azure Arc. "Migrate VMware workloads without changing them, keep vCenter" → Azure VMware Solution.

Portal demoOnboard a server to Azure Arc (generate the script)~3 min

Goal: Show how a server that stays on-premises gets an Azure identity.

  1. Search Azure Arc › Machines › + Add/Create › Add a machine › Add a single server › Generate script.
  2. Choose rg-az305-m12-demo, Central India, OS Windows or Linux, connectivity Public endpoint (or Private endpoint / proxy). Point at the tags page (the same required tags as Module 02).
  3. Show the generated script: it installs the Connected Machine agent and registers the server. Don't run it in class unless you mean to.
  4. Open Azure Arc › Overview: the other Arc types: Kubernetes clusters, SQL Server instances, VMware vCenters, Azure Local.

Say: “An Azure ID card for servers that will never move house.”

12.10

Recap and self-check

Architect's migration checklist

  • Business motivation and success measures written down (CAF Strategy).
  • A complete inventory with performance data and dependencies (Azure Migrate).
  • A strategy per workload, including what to retire and what to retain.
  • A landing zone ready before the first wave (governance, identity, network, monitoring, backup).
  • Waves grouped by dependency, with test migrations and rollback plans.
  • Database migrations planned online or offline according to allowed downtime.
  • Data transfer method chosen by size, bandwidth and one-time vs ongoing.
  • Right-sizing and reservations after the move; Arc for what stays.

Self-check

1. A company must identify all on-premises VMware VMs, their dependencies and the estimated monthly cost in Azure. What do you use?

Azure Migrate discovery and assessment with the appliance, plus dependency analysis; a business case for the TCO comparison.

2. A datacentre lease ends in four months. The apps can't be changed. Which strategy and which tool?

Rehost with Azure Migrate: Migration and modernization (agentless for VMware). If the team must keep VMware tooling, Azure VMware Solution is the alternative.

3. A SQL Server database must move to Azure SQL Managed Instance with only a few minutes of downtime. How?

An online migration with Database Migration Service, or the Managed Instance link for near-zero downtime cut-over.

4. 300 TB of archive data must move to Azure. The internet link is 200 Mbps and shared. What do you recommend?

An offline transfer with Azure Data Box. Over 200 Mbps it would take months.

5. Servers in 50 branch offices will stay on-premises but must be governed by Azure Policy and protected by Defender for Cloud. What do you deploy?

Azure Arc-enabled servers (the Connected Machine agent on each server).

6. Which Cloud Adoption Framework methodology covers preparing the landing zone before migration?

Ready.
