06.1

Why database choice is an architect's call

Imagine this

Think of a bank's paper ledger versus a shopkeeper's notebook. The ledger has fixed columns, every entry balances, and two clerks can never spend the same rupee twice. That's a relational database. The notebook is flexible: one page lists a customer's phone number, the next adds their favourite brand and a sketch of where they live. Nobody minds, because speed and flexibility matter more than strict columns. That's a NoSQL document database. Both are right, for different shops.

Developer view

"I know SQL Server, so we'll use SQL Server. Size? Let's take the biggest one so it's never slow."

Architect view

"What's the data shape and the access pattern? What's the RPO and RTO from Module 01? Does it need to be written in more than one region? Which SQL Server features does the app really use (SQL Agent? cross-database queries?), because that decides VM vs Managed Instance vs Database. Then the smallest tier that meets the SLO, with a plan to scale."

Mindset takeaway

A database decision is really four decisions: engine (shape), deployment (how much you manage), tier (performance and cost) and resilience (how much data and time you can afford to lose). Write all four down, with the "why", in the design document.

06.2

The Azure SQL family

Same engine, three ways to run it

Definition

Azure SQL is a family of managed, secure products built on the SQL Server database engine. SQL Server on Azure Virtual Machines is infrastructure as a service with full control of the OS and instance. Azure SQL Managed Instance is a platform service with near-100% compatibility with SQL Server, deployed into your virtual network. Azure SQL Database is a fully managed platform service for individual databases and elastic pools.

In plain words

All three run the same SQL Server engine. The difference is how much of the building you look after. On a VM you own the whole house. Managed Instance is a furnished flat: the society handles repairs, but you still have your own complete home. SQL Database is a hotel room: you bring only your luggage (the database), and everything else is done for you.

How to pick in under a minute

  1. Does the app need OS access, a SQL Server version or feature that PaaS doesn't support, or third-party software installed beside SQL? → SQL Server on Azure VM.
  2. Does it use instance-level features: SQL Agent jobs, cross-database queries, CLR, Service Broker, linked servers, Database Mail? → SQL Managed Instance.
  3. Otherwise, especially for new apps or SaaS → Azure SQL Database.

Facts worth remembering

  • Azure Hybrid Benefit lets you reuse existing SQL Server licences (with Software Assurance) to cut the vCore price of all three options significantly.
  • SQL Server on a VM gets helpful automation from the SQL IaaS Agent extension: automated patching, automated backup and licence management.
  • Managed Instance sits in a dedicated subnet of your VNet. It's the most "on-prem-like" option, and its Managed Instance link can replicate from an on-prem SQL Server for migration or DR.
  • Azure SQL Database lives on a logical server (<name>.database.windows.net), which is a management boundary for logins, firewall rules and auditing, not a machine you can log in to.
Exam cue

"Requires SQL Server Agent / cross-database queries / CLR", "minimal changes to migrate to PaaS" → SQL Managed Instance. "Requires OS-level access", "SSRS / SSIS / SSAS on the same server", "unsupported SQL Server version" → SQL Server on Azure VM. "New cloud app, minimise administration" → Azure SQL Database.

06.3

Purchasing models and service tiers

Definition

Azure SQL Database offers two purchasing models. The DTU model bundles compute, memory and I/O into preconfigured sizes (Basic, Standard, Premium). The vCore model lets you choose compute and storage independently, in the General Purpose, Business Critical and Hyperscale service tiers, with provisioned or serverless compute.

In plain words

DTU is a thali: one price, a fixed mix of everything. vCore is ordering à la carte: choose how much compute, how much storage, and pay for each. Microsoft recommends vCore for most new designs, because it maps to real hardware, supports Azure Hybrid Benefit and reserved capacity, and makes comparisons with on-prem servers easy.

Exam cue

"Simple bundled pricing", "small workload", "migrate existing DTU database" → stay on DTU. "Azure Hybrid Benefit", "predictable resource sizing", "map to on-premises cores", "new design" → use vCore. Serverless is a compute option inside the vCore General Purpose tier (auto-scales and auto-pauses), not a separate tier.

OptionWhat it gives youChoose it when
General PurposeBalanced compute and remote storage; 99.99% SLAMost business apps; cost matters
Business CriticalLocal SSD, 4 replicas, a free read replica, in-memory OLTP (OLTP: the many small reads and writes of a running business, like placing orders; Module 07 compares it with analytics)Low-latency OLTP, fast failover, reporting on a replica
HyperscaleUp to 128 TB, rapid scale, near-instant backup and restore, up to 30 named replicasLarge or fast-growing databases; heavy read scale-out
Serverless (compute option)Auto-scales vCores within a range and bills per second; General Purpose can auto-pause when idleIntermittent or unpredictable use: dev/test, internal tools, new apps
Elastic poolMany databases share one pool of resourcesMany databases whose peaks happen at different times (SaaS)
DTU: Basic / Standard / PremiumSimple bundled sizesSmall, simple workloads; existing estates already on DTU
Common trap

Serverless isn't "always cheaper". If a database is busy all day, provisioned compute (with reserved capacity) usually costs less. Serverless shines when the database is idle much of the time. Also, after an auto-pause, the first connection waits while the database resumes, so the app must retry.

Exam cue

"Unpredictable or intermittent usage", "pause when not used", "minimise cost for dev/test" → serverless. "Database will grow beyond 4 TB, up to 128 TB" → Hyperscale. "Lowest latency, highest resilience, in-memory OLTP" → Business Critical. "Hundreds of databases with varying load", "multi-tenant SaaS" → elastic pool. "Reuse existing licences" → vCore with Azure Hybrid Benefit.

06.4

Scaling databases

Definition

Scaling up gives one database more compute and memory. Scaling out spreads work over several copies or databases: read scale-out sends read-only queries to replicas, an elastic pool lets many databases share one set of resources, and sharding splits one data set across several databases by a key such as tenant or region.

In Module 01 we said: design for the load you'll have, not the load you fear. Databases give you four ways to grow, and the architect's job is to know which one fits the problem.

Imagine this

A busy dosa stall. Scale up: buy a bigger tawa. Read scale-out: a second counter that only hands out parcels already packed. Elastic pool: five small stalls in a food court sharing one kitchen, because their rush hours differ. Sharding: open branches in Jayanagar, Indiranagar and Whitefield, each serving its own area.

Developer view

"The dashboard is slow. Let's double the vCores."

Architect view

"The dashboard is read-only reporting running against the same primary that takes orders. Move it to the read replica we already pay for in Business Critical, and the checkout gets faster too, without adding a single vCore."

Exam cue

"Offload reporting / read-only workloads" → read scale-out (or a geo-replica, or Hyperscale named replicas). "Many databases, unpredictable individual usage, minimise cost" → elastic pool. "Data too large or busy for one database; partition by tenant" → sharding (Elastic Database tools), or Cosmos DB if the data model allows.

06.5

Availability and disaster recovery

Definition

High availability keeps a database running through local failures (a node, a rack, a zone). Disaster recovery restores service in another region after a regional outage. In Azure SQL, HA is built in, with optional zone redundancy; DR uses active geo-replication or failover groups, and every database also has automated backups for point-in-time restore.

In plain words

Three layers, three questions. HA: "what if a server dies?" Azure handles it. DR: "what if Central India goes dark?" You design it. Backup: "what if someone runs DELETE without a WHERE?" Replicas won't help there, because they faithfully copy the mistake. Only a restore to a point in time will.

Failover groups: the DR answer for most designs

FeatureProtects againstKey facts
Built-in HANode or hardware failureAlways on, in every tier. 99.99% SLA.
Zone redundancyA whole availability zone failingA setting on General Purpose, Business Critical and Hyperscale; up to 99.995% SLA on Business Critical.
Active geo-replicationRegion outageSQL Database only. Up to four readable secondaries, per database, any region. You fail over each database and update connection strings.
Failover groupsRegion outageSQL Database and Managed Instance. A group of databases fails over together, behind listeners that keep the same names.
Point-in-time restoreMistakes, bad deployments, corruptionAutomatic backups; restore to any point in the last 1–35 days (7 by default). Restores create a new database.
Long-term retentionComplianceKeep weekly, monthly or yearly full backups for up to 10 years.
Geo-restoreRegion outage, cheaplyRestore from geo-replicated backups into any region. Slowest and loses the most data, but costs nothing extra.
Imagine this

A failover group is like your company's toll-free number. Customers always dial 1800-xxx-xxxx. If the Bengaluru call centre floods, the number quietly rings in Chennai instead. Customers never learn a new number; they just get through.

Common trap

Geo-replication is asynchronous, so the secondary can be a few seconds behind. If the business says "zero data loss in a regional disaster", be honest: that needs a different design (synchronous writes across regions are slow and expensive). Write the real RPO in the design.

Exam cue

"Fail over several databases together", "connection strings must not change after failover", "Managed Instance DR" → failover group. "Multiple readable secondaries in different regions for one database" → active geo-replication. "Survive a zone failure" → zone-redundant configuration. "Restore data deleted yesterday" → point-in-time restore. "Keep backups 7 years" → long-term retention.

06.6

Protecting data: at rest, in transit, in use

Data has three states. Protect all three.

Transparent Data Encryption (TDE)Encrypts data files, logs and backups in real time. Invisible to apps. On by default for new Azure SQL databases; with customer-managed keys, revoking the key makes the database inaccessible.
Always EncryptedColumns are encrypted in the client driver; keys live in Key Vault, outside the database. Deterministic encryption allows equality lookups; secure enclaves add range queries and pattern matching on encrypted data.
Dynamic data maskingShows XXXX-XXXX-XXXX-1234 to users who don't have the UNMASK permission. It's a presentation control, not encryption: the real data is unchanged.
Row-level securityA predicate decides which rows each user sees, such as "store managers see only their own store".
Microsoft Entra authenticationUsers, groups and managed identities sign in with Entra ID, with MFA and Conditional Access. Entra-only authentication turns SQL logins off completely.
Auditing, Defender for SQL and ledgerAuditing records who ran what (to a workspace, storage or Event Hubs). Defender for SQL finds vulnerabilities and alerts on threats like SQL injection. Ledger makes tampering cryptographically evident.
Common trap

"Encrypt the credit card column so DBAs can't see it" is not TDE (DBAs see plaintext through TDE) and not masking (admins can unmask). The answer is Always Encrypted. And for real card numbers, the better PCI answer is not to store them at all: let a payment provider tokenise them.

Exam cue

"Encrypt data at rest, no app changes" → TDE. "Company must manage / rotate / revoke the encryption key" → TDE with customer-managed key in Key Vault. "Protect sensitive columns from high-privilege users / DBAs / cloud operators" → Always Encrypted. "Show only the last four digits to support staff" → dynamic data masking. "Users see only their own rows" → row-level security. "Detect SQL injection attempts" → Microsoft Defender for SQL.

  2. Server › Security › Microsoft Defender for SQL: vulnerability assessment and threat protection (SQL injection alerts).

  • You're the Entra admin, so you'll still see unmasked data. Masking is a presentation control, not encryption.

Say: “TDE protects the disk, TLS the wire, Always Encrypted protects the data from everyone without the key.”

06.7

Open-source databases and SQL at the edge

Azure Database for PostgreSQL and MySQL

Definition

Azure Database for PostgreSQL and Azure Database for MySQL are fully managed database services for the community editions of those engines. The flexible server deployment option provides control over configuration and maintenance windows, zone-redundant high availability, read replicas, automated backups and Burstable, General Purpose or Memory Optimized compute.

In plain words

If the app was built on PostgreSQL or MySQL, don't force it onto SQL Server. Keep the engine the developers know, and let Azure do the patching, backups and HA. Burstable is the low-cost choice for small or quiet workloads.

Name check

"Single Server" for PostgreSQL and MySQL has been retired; flexible server is the only deployment option for new designs. Azure Database for MariaDB has also been retired; migrate to MySQL flexible server.

Azure SQL Edge (retired)

Azure SQL Edge was a small-footprint SQL engine for IoT gateways and edge devices, with built-in data streaming and time-series support. It was retired in September 2025.

Name check

You may still meet SQL Edge in older practice questions ("store and analyse IoT data on the device, even when disconnected"). For new designs, run SQL Server in a container (for example, on Linux) on the edge device, and sync or stream to Azure when connected. Know what SQL Edge was, but don't design with it.

Exam cue

"Existing PostgreSQL / MySQL app", "open-source engine, managed" → Azure Database for PostgreSQL / MySQL flexible server. "Low cost for a small, mostly idle open-source DB" → Burstable tier.

06.8

Azure Cosmos DB

A globally distributed database for any scale

Definition

Azure Cosmos DB is a fully managed, globally distributed NoSQL and relational database with single-digit millisecond response times, automatic and instant scalability, and SLAs covering availability, throughput, latency and consistency. It offers several APIs, including NoSQL, MongoDB, Apache Cassandra, Apache Gremlin and Table, so applications can use familiar data models and drivers.

In plain words

Cosmos DB is the database for "millions of users, all over the world, and every millisecond counts". You store JSON documents (or key-value, column or graph data), click a map to add regions, and Azure keeps a copy close to every user. You pay for throughput, not for servers.

The four ideas you must know

Request Units (RU/s)The currency of Cosmos DB. Reading a 1 KB item by its id and partition key costs about 1 RU; writes and queries cost more. Choose provisioned (manual or autoscale) or serverless (pay per request, for spiky or small workloads).
Partition keyThe property that spreads your data and load across partitions, such as /customerId. Pick one with many distinct values that's used in most queries. A logical partition holds up to 20 GB. Changing the key later means moving the data.
Global distributionAdd or remove regions at any time. Enable multi-region writes to accept writes everywhere, for up to 99.999% availability.
Consistency levelsFive levels between "always the latest" and "fastest possible". This is the most-tested Cosmos DB topic. See the diagram.
Imagine this

A cricket score. Strong is being at the stadium: you see every ball as it's bowled. Bounded staleness is TV with a fixed 10-second delay. Session is your own scorecard app: whatever you entered, you see straight away. Consistent prefix is the newspaper: a day late, but the overs are in the right order. Eventual is the WhatsApp group: everybody gets the score in the end, but messages sometimes arrive out of order.

Which API?

APIData modelChoose when
NoSQL (native)JSON documents, SQL-like queriesNew apps. Newest features first (e.g. vector search for AI apps).
MongoDBBSON documentsExisting MongoDB apps and skills. RU-based or vCore-based options.
Apache CassandraWide-columnExisting Cassandra workloads, without running clusters.
Apache GremlinGraphRelationships first: social networks, recommendations, fraud rings.
TableKey-valueUpgrade from Azure Table Storage with no code change.

Table Storage or Cosmos DB for Table?

Azure Table Storage

Part of a storage account. Very cheap, simple key-value. Indexes only PartitionKey and RowKey. No latency guarantees; geo-replication through GRS only.

Cosmos DB for Table

Same API and SDK. Single-digit millisecond latency, every property indexed automatically, throughput SLAs, turnkey global distribution and multi-region writes. Costs more.

Facts worth remembering

  • The free tier gives the first 1,000 RU/s and 25 GB free on one account per subscription. Ideal for demos and small apps.
  • The change feed streams every insert and update in order, so you can trigger functions, update caches or build event-driven designs (Module 10).
  • Backups are periodic by default; continuous backup gives point-in-time restore over the last 7 or 30 days.
  • For analytics on Cosmos DB data without hurting the live app, use Microsoft Fabric mirroring (the newer path), or Azure Synapse Link on existing designs.
Exam cue

"Globally distributed", "multi-region writes", "single-digit millisecond latency anywhere", "99.999%" → Cosmos DB. "Users must always see their own updates, best performance otherwise" → Session. "Reads must never be stale" → Strong. "Existing MongoDB / Cassandra app, minimal changes" → the matching API. "Upgrade Table Storage for global, low-latency access" → Cosmos DB for Table. "Spiky, low-traffic workload" → serverless; "variable but sustained" → autoscale.

06.9

Choosing the right database

The whiteboard version, read from left to right: "If the requirement says… then choose…"

If the requirement says…Choose
New relational app, minimal admin, elastic scaleAzure SQL Database (serverless or provisioned; Hyperscale if large)
Many small databases for different customers (SaaS)Azure SQL Database elastic pool
Migrate SQL Server with SQL Agent, cross-database queries, minimal changeAzure SQL Managed Instance
Needs OS access, SSRS/SSAS on the same box, or an unsupported versionSQL Server on Azure VM
Existing PostgreSQL or MySQL appAzure Database for PostgreSQL / MySQL (flexible server)
Global users, multi-region writes, flexible JSON schema, millisecond latencyAzure Cosmos DB (NoSQL API)
Graph relationshipsCosmos DB for Apache Gremlin
Cheap key-value at small scaleAzure Table Storage
A fast in-memory cache in front of the databaseAzure Managed Redis (the successor to Azure Cache for Redis)
Analytics over terabytes of historyNot an OLTP database: a data lake + Synapse / Fabric (Module 07)
Mindset takeaway

Real systems use more than one database. Orders in Azure SQL (transactions), the product catalogue in Cosmos DB (global, flexible), sessions in Redis (speed), history in a data lake (analytics). The architect's skill is drawing the line between them, not forcing everything into one.

06.10

Meridian: the database design

Meridian Retail· applying Module 06

Today Meridian runs dozens of SQL Server databases in its datacentre: an orders system, a merchandising ERP full of SQL Agent jobs and cross-database queries, one vendor app stuck on an old SQL Server version, and a small inventory database for every store. The new online store adds a product catalogue and shopping carts. Leadership's goal: checkout survives a regional outage, and PCI DSS for payments.

06.11

Recap and self-check

Architect's database checklist

  • Engine chosen by data shape and access pattern; more than one engine where it helps.
  • Deployment option justified: VM only for OS needs, Managed Instance for instance features, SQL Database otherwise.
  • Tier sized for today with a scaling path: scale up, read scale-out, elastic pool or sharding.
  • RPO and RTO written down; zone redundancy and a failover group (or geo-replication) to match.
  • Backup retention set for mistakes (point-in-time) and compliance (long-term).
  • Data protected at rest (TDE, keys), in transit (TLS, private endpoints) and in use (Always Encrypted, masking, RLS).
  • Entra authentication with managed identities; auditing and Defender switched on.
  • For Cosmos DB: partition key, consistency level, throughput model and regions decided deliberately.

Self-check

1. An on-prem SQL Server app uses SQL Agent jobs and cross-database queries. The company wants PaaS with minimal changes. Which option?

Azure SQL Managed Instance. It supports instance-level features such as SQL Agent and cross-database queries, which Azure SQL Database doesn't.

2. Twenty databases must fail over to another region together, and the application's connection strings must not change. What do you use?

A failover group. It fails over a group of databases together, and the read-write and read-only listener names stay the same after failover.

3. A dev/test database is used only a few hours a week. How do you minimise cost?

Azure SQL Database serverless (General Purpose) with auto-pause. You pay for compute only while it runs, plus storage.

4. Support staff must see only the last four digits of customer phone numbers, while DBAs must not be able to read customers' national ID numbers at all. Which two features?

Dynamic data masking for the phone numbers (a presentation control), and Always Encrypted for the national IDs, because keys held outside the database mean even DBAs see only ciphertext.

5. A global app on Cosmos DB must let users always see their own changes straight away, with the best possible performance otherwise. Which consistency level?

Session, the default. It guarantees read-your-own-writes within a session while keeping latency low.

6. A database will grow to 60 TB and needs fast backups and restores. Which tier?

Hyperscale. It supports up to 128 TB, with snapshot-based backups and fast restores regardless of size.

Carry this into Module 07

Operational databases run the business today. But leadership's questions ("Which stores are losing money? What will sell next Diwali?") need years of data from many systems, joined and cleaned. That's a different job, with different tools: data integration and analytics.
