Compute: Choosing Where Your Code Runs

Give five developers the same app and you'll get five hosting answers: "a VM, obviously", "Kubernetes, obviously", "serverless, obviously"… Each one is right for some app and expensive for the rest. 09.0

The mental map

Every Azure compute service sits on one slope. At the top left you control everything and manage everything. At the bottom right you write a function and Azure does the rest. Moving right buys you less work and faster scaling, and costs you control. The architect's job is to stop as far right as the workload allows.

09.1

How much do you want to manage?

Imagine this

Getting lunch for your team. You can buy a plot and build a kitchen (on-premises), rent a flat with a kitchen and cook yourself (a VM: you buy the vegetables, clean the gas stove, fix the tap), hire a caterer who cooks in a shared kitchen to your menu (App Service, containers), or order from Swiggy and pay per plate (Functions). Nobody is "right". A wedding needs a caterer; a Tuesday lunch for three needs Swiggy; a restaurant with a secret recipe needs its own kitchen.

Developer view

"Kubernetes is what modern teams use. Let's put everything on AKS."

Architect view

"Kubernetes is a platform to run, with upgrades, node pools, networking and security of its own. For twelve stateless APIs, Container Apps or App Service gives the same outcome without a platform team. I pick AKS when we need what only Kubernetes gives."

Mindset takeaway

The first compute question is never "which service is best?" It is "what is the least we can manage and still meet the requirements?" Every requirement that pushes you left (an OS-level agent, a custom kernel, a licence tied to a host) should be named out loud.

09.2

Virtual machines

Full control, full responsibility

Definition

Azure Virtual Machines provide on-demand, scalable computing resources with full control of the operating system. You choose the image (Windows or Linux), the size (vCPU, memory, storage and network capacity), managed disks and the network, and you are responsible for configuring, patching and maintaining the software that runs on the VM.

In plain words

A VM is a server you rent by the second. It behaves like the server in your datacentre: you log in, install what you want, and own the patching. Pick it when something needs the OS itself: a legacy app, an agent, a specific Windows feature, or software whose licence is tied to a server.

Sizes, in one table

FamilyBuilt forTypical use
B (burstable)Low baseline CPU, bursts when neededDev/test, small web servers, jump boxes
D (general purpose)Balanced CPU and memoryMost production apps, app servers
E / M (memory)High memory per vCPU (M is very large)Databases, SAP HANA, in-memory caches
F (compute)High CPU per GB of memoryBatch, gaming servers, analytics workers
L (storage)Fast local NVMe storageNoSQL databases, data warehousing
N (GPU) / H (HPC)GPUs, or fast interconnect for HPCAI training and inference, rendering, simulations

The cost levers every architect should pull

ReservationsCommit to a specific VM size and region for 1 or 3 years for a large discount (up to about 70%). Best for steady 24x7 workloads.
Azure savings plan for computeCommit to a hourly spend for 1 or 3 years, usable across sizes, regions and services (VMs, App Service, Functions Premium, Container Apps). Less discount, more flexibility.
Azure Hybrid BenefitBring your existing Windows Server and SQL Server licences (with Software Assurance) and pay only for the base compute. A big saving in migrations.
Spot VMsSpare capacity at up to 90% off, but Azure can evict the VM with 30 seconds' notice. For interruptible work: batch, render, CI agents, test.
Right-size and shut downAzure Advisor recommends smaller sizes; auto-shutdown for dev VMs at 8 p.m. saves more than half the bill.
Dedicated HostA whole physical server just for you. Not a cost saver: it's for compliance or licences that require physical isolation.
Good practice: security defaults

New VMs use Trusted Launch (Secure Boot and vTPM) by default. Add encryption at host, no public IP (reach it through Azure Bastion, Module 11), Update Manager for patching, and Defender for Servers. A VM is your OS to defend.

Developer view

"I'll pick a big VM so it never runs out of capacity."

Architect view

"Size for the measured load, scale out with a scale set for peaks, and cover the steady baseline with a reservation or savings plan. A D16 running at 6% CPU is a donation to Microsoft."

Exam cue

"Full control of the OS", "install a custom agent", "legacy app", "lift and shift" → VMs. "Workload can be interrupted, minimise cost" → Spot VMs. "Runs 24x7 for 3 years" → reserved instances (or savings plan if sizes and regions change). "Existing Windows Server / SQL licences" → Azure Hybrid Benefit. "Physical isolation for compliance" → Dedicated Host.

09.3

Virtual Machine Scale Sets

Identical VMs that grow and shrink with demand

Definition

Azure Virtual Machine Scale Sets let you create and manage a group of load-balanced VMs. The number of instances can automatically increase or decrease in response to demand or a schedule. Flexible orchestration (the recommended mode) spreads instances across availability zones and fault domains and lets you mix VM sizes and Spot with regular capacity.

Imagine this

Billing counters at a supermarket during the Diwali sale. The manager opens more counters when the queue gets long and closes them when it's quiet. Every counter works the same way. A scale set is that manager, watching CPU (the queue length) and opening identical VMs (counters).

Common trap

Autoscaling a VM that keeps state on its local disk (sessions, uploaded files). The new instances don't have it and scale-in deletes it. Make instances stateless first: sessions in Redis (Module 10), files in Blob or Azure Files.

Exam cue

"Automatically scale identical VMs", "hundreds of VMs from one image", "IaaS with autoscale" → Virtual Machine Scale Sets. "Mix Spot and regular VMs", "spread across zones" → flexible orchestration.

Portal demoWrite autoscale rules for a scale set, then cancel~3 min

Goal: Show flexible orchestration, zones and an autoscale rule in one form.

  1. Search Virtual machine scale sets › + Create: Central India, Availability zone 1, 2, 3; orchestration mode Flexible.
  2. Point at Scale set Spot/standard mix (run part of the capacity on Spot), if shown in your region.
  3. Scaling tab: scaling policy Autoscaling › Configure: default min 2, max 10; add a rule CPU > 70% for 10 minutes → +2, and a scale-in rule. Point at the schedule option for sale days.
  4. Networking tab: show the option to put a load balancer in front. Cancel.

Say: “The supermarket manager opening counters when the queue grows.”

09.4

Azure App Service

Bring your code, get a website

Definition

Azure App Service is a fully managed HTTP-based platform for hosting web applications, REST APIs and mobile back ends in .NET, Java, Node.js, Python and PHP, or as custom containers, on Windows or Linux. Apps run in an App Service plan, which defines the region, the instance size and count, and the features available, and provides built-in autoscale, deployment slots, authentication and patching.

In plain words

You push code from GitHub; Azure gives you a URL with HTTPS, patched servers, autoscale and a staging slot. The plan is the hardware you pay for; the apps are tenants living on it. Several small apps can share one plan, and therefore one bill.

Plan tierWhat you getUse it for
Free / SharedShared hardware, no SLA, no custom scaleLearning and quick prototypes
BasicDedicated instances, manual scale, custom domains and TLSDev/test, low-traffic sites
StandardAutoscale, deployment slots, daily backupsProduction web apps
Premium (v3 and newer)Faster hardware, more slots and instances, zone redundancyBusy or business-critical production
Isolated v2 (App Service Environment v3)A single-tenant deployment inside your VNet, very high scaleStrict isolation and compliance, internal-only apps at scale

Facts worth remembering

  • Scale up = a bigger plan tier or size. Scale out = more instances (manual, autoscale rules, or automatic scaling on Premium).
  • VNet integration lets the app call private resources (outbound). Private endpoints make the app itself private (inbound). Both are Module 11 ideas.
  • Built-in authentication ("Easy Auth") signs users in with Entra ID or other providers without code.
  • Managed identity to reach SQL, Storage and Key Vault without secrets (Module 03).
  • WebJobs run background scripts on the same plan; for anything serious, consider Functions.
Exam cue

"Web app or API, minimise management", ".NET / Java / Node / Python", "deployment slots", "zero-downtime deployment" → App Service (Standard or higher for slots and autoscale). "Single-tenant, fully isolated in a VNet", "internal-only, high scale" → App Service Environment v3 (Isolated v2).

09.5

Containers without Kubernetes

A container packages an app with everything it needs (runtime, libraries, config) into one image that runs the same on a laptop and in the cloud. Images live in a registry: Azure Container Registry (ACR). The question is what runs them. Two Azure services do it without asking you to operate a cluster.

Imagine this

A container is a tiffin box: the whole meal, sealed, same taste whichever office it's opened in. Container Instances is handing one tiffin to one person for one lunch. Container Apps is a canteen that serves as many identical tiffins as there are people in the queue, and closes the counter when nobody is there.

Azure Container Instances (ACI)

Definition

Azure Container Instances runs containers on demand in a managed, serverless environment, without virtual machines or orchestration. A container group (one or more containers sharing a lifecycle, network and storage) starts in seconds and is billed per second for the vCPU and memory it uses.

In plain words

"Run this one container, now." No scaling rules, no load balancing, no rolling upgrades. Great for short tasks, build agents, a quick test, or as burst capacity behind AKS (virtual nodes).

Azure Container Apps

Definition

Azure Container Apps is a serverless platform for running containerised applications and microservices. It is built on Kubernetes and open-source projects (KEDA for event-driven autoscaling, Dapr for service-to-service building blocks, Envoy for ingress) but does not expose the Kubernetes API. Apps scale on HTTP traffic, CPU, memory or events, including scale to zero, and support revisions for traffic splitting and container jobs for scheduled or event-triggered tasks.

In plain words

Most of what teams actually want from Kubernetes (autoscale, microservices talking to each other, blue-green releases, background workers scaling on a queue) without running Kubernetes. Apps share an environment (a secure boundary with its own VNet and logs). Pay per use on the Consumption profile, or reserve dedicated workload profiles (including GPUs) for steady loads.

Container InstancesContainer AppsAKS
You manageOne container groupApps and their scale rulesThe cluster, node pools, upgrades, add-ons
AutoscaleNoYes, incl. scale to zero on events (KEDA)Yes (HPA, KEDA, cluster autoscaler)
Kubernetes APINoNoYes, full
Best forSimple, short-lived or one-off tasksMicroservices, APIs, event-driven workersComplex platforms, full control, existing K8s skills
Exam cue

"Run a container quickly, no orchestration", "simple, short-lived", "billed per second" → Container Instances. "Microservices, serverless containers, scale to zero", "event-driven scaling with KEDA", "Dapr", "no need to manage Kubernetes" → Container Apps.

09.6

Azure Kubernetes Service

Kubernetes, with the control plane managed for you

Definition

Azure Kubernetes Service (AKS) is a managed Kubernetes service. Azure operates the Kubernetes control plane (API server, scheduler, etcd); you manage the node pools (VMs that run your pods) and the workloads. AKS integrates with Entra ID, Azure networking, Azure Monitor, Azure Policy and Container Registry.

In plain words

Kubernetes is an operating system for a fleet of servers: you tell it "I want 6 copies of this container, always", and it places them, restarts them and spreads them out. AKS runs the brain of Kubernetes for you. The body (the nodes) is still yours to size, upgrade and secure. AKS Automatic goes further and manages node pools, scaling and many settings for you.

Facts worth remembering

  • Pricing tiers for the control plane: Free (no SLA, for dev/test), Standard (financially backed uptime SLA, for production) and Premium (adds long-term support for Kubernetes versions).
  • Workload identity lets a pod use an Entra identity to reach Key Vault or Storage, with no secrets in the cluster.
  • Networking: Azure CNI Overlay is the common default (pods get IPs from a private overlay range, saving VNet addresses).
  • You must upgrade Kubernetes versions regularly; each version is supported for about a year. Plan for it like patching.
Common trap

Choosing AKS for a handful of web apps because "it's the standard". The team then spends its time on upgrades, ingress controllers and node patching instead of features. If the requirement list doesn't mention Kubernetes-specific needs (custom operators, service mesh, portability across clouds, existing Helm charts and K8s skills), check Container Apps first.

Exam cue

"Kubernetes", "orchestrate containers with full control", "Helm", "existing K8s manifests", "custom operators", "portability" → AKS. "Reduce node cost for interruptible pods" → a Spot node pool. "Pods access Key Vault without secrets" → workload identity.

Portal demoWalk the AKS create form: tiers, node pools and networking~4 min

Point out while you are there

  • Count the decisions on this form. Every one of them is a reason to ask whether Container Apps would do.

Say: “Azure runs the brain; you still run the body.”

09.7

Azure Functions

Code that runs when something happens

Definition

Azure Functions is a serverless, event-driven compute service. A function runs in response to a trigger (HTTP request, timer, queue or Service Bus message, blob created, Event Grid or Event Hubs event, Cosmos DB change) and uses bindings to read from and write to other services with little code. Hosting plans determine scaling, limits and billing; Durable Functions adds stateful workflows.

In plain words

"When a photo lands in this container, make a thumbnail." "Every night at 2 a.m., close yesterday's tills." You write just that piece of code. Azure starts it when the event happens, runs as many copies as there are events, and (on the right plan) charges you only while it runs.

Hosting planScaling and billingPick it when
Flex ConsumptionScale to zero, fast scale out, pay per execution and memory; optional always-ready instances; VNet integrationThe default for new serverless apps, especially on Linux
Consumption (classic)Scale to zero, pay per execution; default timeout 5 min, max 10 min; cold startsExisting apps, light and spiky workloads
Premium (Elastic Premium)Pre-warmed instances (no cold start), VNet integration, longer runs; billed per instance-hourSteady traffic, latency-sensitive, long-running functions
Dedicated (App Service plan)Runs on an App Service plan you already pay forSpare capacity on an existing plan, predictable cost
Container AppsFunctions packaged as containers in a Container Apps environmentFunctions alongside other microservices
Name check

Microsoft now points new Linux serverless apps to Flex Consumption; the classic Linux Consumption plan is on a retirement path. On the exam, "Consumption" still means "pay only when it runs, scales to zero, short executions", and "Premium" still means "no cold start, VNet, longer runs".

Durable Functions in one picture

WhatStateful workflows written as code: an orchestrator function calls activity functions and remembers where it got to, even across restarts.
WhyPlain functions are stateless and short. Real processes ("charge card, reserve stock, wait for courier, send invoice") are long and multi-step.
WhenFunction chaining, fan-out/fan-in, waiting for a human approval, or a long-running process with retries and compensation.
Developer view

"Serverless is always cheapest, because you only pay when it runs."

Architect view

"Per-execution billing wins for spiky or idle workloads. A function running flat out 24x7 can cost more than a small App Service plan. I look at the traffic shape, the cold-start tolerance and the execution time before I pick the plan."

Exam cue

"Event-driven", "runs when a file is uploaded / message arrives / on a schedule", "pay only when code runs", "minimise cost for sporadic workloads" → Functions (Consumption / Flex Consumption). "Avoid cold starts", "connect to a VNet", "run longer than 10 minutes" → Premium (or Flex). "Stateful workflow, fan-out/fan-in, wait for human approval" → Durable Functions.

09.8

Azure Batch

A thousand VMs for an afternoon

Definition

Azure Batch runs large-scale parallel and high-performance computing (HPC) jobs efficiently in Azure. It creates and manages a pool of compute nodes (VMs), installs the applications, and schedules jobs made of many tasks onto those nodes. There's no extra charge for Batch itself; you pay for the VMs, storage and networking used.

Imagine this

Board exam results. Two million answer sheets, each marked independently. You don't hire one superhuman examiner: you hire 2,000 examiners for a week, give each a bundle, and let them go home when the bundles are done. Batch is the exam controller who hires, hands out bundles, re-assigns a bundle if an examiner falls ill, and lets everyone go at the end.

  • Fits embarrassingly parallel work: rendering frames, Monte Carlo risk models, genome analysis, transcoding video, processing millions of images.
  • Pools can autoscale with a formula, and mix dedicated nodes with Spot nodes for big savings.
  • Tightly coupled HPC (nodes talking constantly, MPI) uses H-series VMs with InfiniBand.
Exam cue

"Large-scale parallel", "HPC", "rendering", "thousands of tasks", "schedule jobs on a pool of VMs", "no infrastructure to manage for the scheduler" → Azure Batch. Add "lowest cost, can be interrupted" → Batch with Spot nodes.

Portal demoSee pools, jobs and tasks in a Batch account~3 min

Goal: Connect the exam-controller analogy to Batch's three objects.

  1. Search Batch accounts › + Create: name, Central India, optional storage account, pool allocation mode Batch service. Create it if time allows (Batch itself is free; you pay for nodes).
  2. Open it › Pools › + Add: image, VM size, Target dedicated nodes and Target Spot/low-priority nodes, and Auto scale with a formula. Cancel: don't create a pool.
  3. Point at Jobs and, inside a job, Tasks: a job is the stack of answer sheets, tasks are the bundles.

Say: “Hire 2,000 examiners for a weekend, then send everyone home.”

09.11

Recap and self-check

Architect's compute checklist

  • Started from "the least we can manage", and named every requirement that pushed left.
  • Compute chosen per workload, not one platform for everything.
  • VMs sized from measurements, with reservations, savings plan, Hybrid Benefit and Spot considered.
  • Instances stateless, so scale sets, App Service and containers can scale out and in.
  • App Service tier chosen for the features needed: slots, autoscale, zones, isolation.
  • Containers placed on ACI, Container Apps or AKS based on the control actually needed.
  • Functions plan chosen for traffic shape, cold-start tolerance, run time and networking.
  • Each choice has a continuity story (Module 08) and a security baseline (Part I).

Self-check

1. A legacy Windows app needs a third-party monitoring agent installed on the OS and a specific registry setting. Where does it run?

On Azure Virtual Machines (or a scale set if it must autoscale). PaaS options don't give OS-level control.

2. A team runs twelve containerised microservices. They want autoscale on queue length, scale to zero at night, and no Kubernetes to manage. Which service?

Azure Container Apps: serverless containers with KEDA-based event scaling and scale to zero.

3. A web app must support zero-downtime releases with an instant rollback. What do you use, and what is the minimum tier?

App Service deployment slots with swap. Slots need the Standard tier or higher.

4. Images uploaded to Blob storage must be resized within seconds. Uploads are unpredictable, sometimes none for hours. Minimise cost.

Azure Functions on a Consumption or Flex Consumption plan, triggered by blob-created events (Event Grid). It scales to zero when there are no uploads.

5. An engineering firm must render 50,000 frames over a weekend at the lowest cost. The job tolerates interruptions. Design?

Azure Batch with a pool of Spot nodes (and a few dedicated nodes if a deadline matters). Batch reschedules tasks from evicted nodes.

6. A company has Windows Server licences with Software Assurance and will run 40 VMs 24x7 for three years. Which two cost levers apply?

Azure Hybrid Benefit for the Windows licences, and 3-year reservations (or a savings plan if sizes and regions may change).

Carry this into Module 10

Choosing compute decides where each piece of code runs. The next question is how they talk. If the storefront calls the order service directly and the order service is slow, the storefront is slow too. Module 10 adds queues, events, an API gateway and a cache so the pieces can fail, scale and change independently.
