The mental map

Every analytics platform, from a startup's first dashboard to a bank's data estate, is the same five stages: sources → ingest → store → process → serve. The services in this module each own one or two of those stages. Place each service on this picture and the comparisons stop being confusing.

07.1

Why analytics is a separate design

Imagine this

A busy restaurant. The billing counter is built for speed: one order at a time, correct to the rupee, never down at lunchtime. That's your operational database (Module 06). The owner's monthly review is a different job: every bill from every branch for three years, joined with supplier invoices and the weather, to decide next year's menu. If the owner ran that review on the billing counter during the lunch rush, the queue would reach the street. So you copy the bills to a back office (the lake), clean them up, and analyse them there.

OLTP: running the business

Many small reads and writes, a few rows each, millisecond response, strict transactions. "Place this order." Azure SQL, Cosmos DB.

OLAP: understanding the business

Few, huge queries across millions of rows and many sources, seconds to minutes are fine. "Sales by store by week for three years." Data lake, Synapse, Databricks, Fabric.

Developer view

"The CEO wants a sales report? I'll write a SQL query against the orders database and put it behind a button."

Architect view

"Reports belong on a copy built for reading: a lake fed by pipelines, cleaned in layers, and served to Power BI. Then the checkout never slows down because someone opened a dashboard, and we can join in data from systems the orders database has never heard of."

Mindset takeaway

Separate the system that records from the system that explains. Each can then be designed, scaled, secured and paid for according to its own job.

07.2

The vocabulary, in plain words

Analytics questions are full of jargon. Here are the eight terms you need, each in one line.

BatchProcess data in chunks on a schedule: "every night at 2 a.m., load yesterday's sales".
StreamingProcess each event within seconds of it happening: "alert when a store's card terminal fails five times in a minute".
ETLExtract, Transform, then Load. Clean the data on the way in, in a separate engine. The classic warehouse approach.
ELTExtract, Load raw data first, then Transform inside the lake or warehouse with its own compute. The modern cloud default.
Data warehouseClean, structured, modelled data (often a star schema) for SQL reporting. Fast and trusted, but rigid.
Data lakeCheap storage for any data in its raw form: CSV, JSON, Parquet, images, logs. Flexible, but it can become a swamp without governance.
LakehouseA lake with warehouse behaviour: table formats like Delta Lake add transactions, schema and versioning to files in the lake.
Parquet / DeltaColumn-based file formats. Analytics reads a few columns from millions of rows, so they are much faster and cheaper than CSV.
Exam cue

"Results needed within seconds", "real-time dashboard", "continuous events" → streaming. "Nightly load", "scheduled", "historical" → batch. "Store data in native/raw format for future use" → data lake. "Structured data for SQL reporting, star schema" → data warehouse.

07.3

Azure Data Lake Storage Gen2

The foundation every analytics design sits on

Definition

Azure Data Lake Storage Gen2 is a set of big-data analytics capabilities built on Azure Blob Storage. Enabling the hierarchical namespace on a storage account organises objects into real directories, enables atomic directory operations and POSIX-style access control lists (ACLs), and exposes a Hadoop-compatible endpoint (ABFS) used by Spark, Databricks, Synapse and Fabric.

In plain words

ADLS Gen2 is Blob storage with real folders. In plain Blob, a "folder" is just part of a file name, so renaming a folder of a million files means copying a million files. With the hierarchical namespace switched on, renaming the folder is one instant operation, and you can set permissions per folder. Big-data engines love both.

The medallion pattern: bronze, silver, gold

Facts worth remembering

  • The hierarchical namespace is a checkbox on the storage account (Standard GPv2 or Premium block blob). An existing account can be upgraded to it, but it can't be switched off again.
  • Access is controlled by Azure RBAC (coarse, for the whole account or container) plus ACLs (fine-grained, per directory and file). RBAC is evaluated first.
  • Everything from Module 05 still applies: redundancy, tiers, lifecycle management, private endpoints, encryption with your own keys.
  • Engines use the abfss://container@account.dfs.core.windows.net/path address. Note dfs, not blob.
Name check

Data Lake Storage Gen1 (a separate service) was retired in February 2024. Any "Data Lake Store" in a new design means Gen2: a storage account with the hierarchical namespace enabled.

Exam cue

"Store large volumes of structured and unstructured data for big-data analytics", "hierarchical file system", "POSIX ACLs", "Hadoop-compatible" → ADLS Gen2. "Grant a team access to one folder only" → ACLs on that directory.

07.4

Azure Data Factory

The conductor of your data pipelines

Definition

Azure Data Factory (ADF) is a fully managed, serverless cloud service for data integration. It creates data-driven workflows (pipelines) that orchestrate data movement and transformation at scale, with more than 90 built-in connectors, code-free mapping data flows, scheduling and event triggers, and monitoring.

In plain words

ADF is the dabbawala system of your data. It picks up from hundreds of places, knows exactly where each box must go and by when, hands boxes to the right people for processing, and tells you immediately if one went missing. It doesn't cook the food itself. Heavy transformation is often done by Databricks or Synapse, with ADF calling them in the right order.

Integration runtimeRuns whereUse it when
Azure IRMicrosoft-managed compute in Azure (optionally in a managed VNet with private endpoints)Cloud-to-cloud copies and data flows
Self-hosted IRSoftware you install on a Windows machine on-premises or in your VNetThe source is on-premises or behind a firewall or private network
Azure-SSIS IRA managed cluster that runs SQL Server Integration ServicesLift and shift existing SSIS packages without rewriting them
Developer view

"I'll write a Python script that copies the files every night and run it from cron on a VM."

Architect view

"A script has no retries, no lineage, no monitoring and one person who understands it. ADF gives us managed retries, alerts on failure, Git-based CI/CD, Key Vault for secrets, and a managed identity to reach the lake without passwords."

Exam cue

"Orchestrate data movement", "copy data from 90+ sources", "schedule or event-based pipelines", "code-free ETL" → Data Factory. "Source is an on-premises SQL Server" → self-hosted integration runtime. "Run existing SSIS packages in Azure" → Azure-SSIS IR. "Start the pipeline when a file arrives in storage" → storage event trigger.

07.5

Azure Databricks

The data engineer's and data scientist's workshop

Definition

Azure Databricks is a unified, open analytics platform for building, deploying and maintaining data, analytics and AI solutions at scale, built on Apache Spark. It provides collaborative notebooks, managed Spark clusters and serverless compute, SQL warehouses, Delta Lake for reliable tables on the data lake, Unity Catalog for governance, and MLflow for the machine learning lifecycle.

In plain words

Databricks is where people who write Python, SQL or Scala clean huge data sets and train machine learning models, together, in shared notebooks. Under the hood, Spark splits the job across many machines, so a transformation over a billion rows finishes in minutes instead of days.

Imagine this

A wedding caterer's kitchen for 5,000 guests. One cook couldn't do it in a week. So the head chef (the Spark driver) splits the work: twenty cooks (worker nodes) each chop, fry and pack their share at the same time. The recipe book everyone shares is the notebook. When the wedding's over, the extra cooks go home, and you stop paying them (auto-termination).

WorkspaceThe Azure resource and the web UI where notebooks, jobs and data live. Choose the Premium tier for Unity Catalog, role-based controls and most security features.
ComputeAll-purpose clusters for interactive work, job clusters (cheaper) for scheduled pipelines, serverless for instant start, and SQL warehouses for BI queries.
Delta LakeTurns Parquet files in ADLS into tables with ACID transactions, schema enforcement and time travel. The heart of the lakehouse.
Unity CatalogOne place to govern tables, files, permissions and lineage across workspaces.
Common trap

A forgotten all-purpose cluster runs all weekend and the bill arrives on Monday. Always set auto-termination, use job clusters for scheduled work, and put cluster policies in place so nobody can start a 50-node cluster by accident.

Exam cue

"Data scientists and engineers collaborate in notebooks", "Apache Spark", "machine learning on big data", "Python / Scala / R", "lakehouse with Delta Lake" → Azure Databricks.

07.6

Azure Synapse Analytics

Warehouse, lake queries and Spark under one roof

Definition

Azure Synapse Analytics is an enterprise analytics service that brings together data warehousing and big-data analytics. A Synapse workspace offers dedicated SQL pools (provisioned massively parallel data warehousing), a serverless SQL pool for querying files in the data lake, Apache Spark pools, Synapse pipelines (the Data Factory engine) and Synapse Link, all managed in Synapse Studio.

In plain words

Synapse is a food court under one roof. One counter is the big, always-ready restaurant (the dedicated SQL pool: your data warehouse). Another is "pay per plate" (serverless SQL: just query files in the lake, pay for what you read). A third is the Spark kitchen. They share one entrance (Synapse Studio), one lake and one security model.

Dedicated SQL poolServerless SQL poolApache Spark pool
What it isA provisioned MPP data warehouse (formerly SQL DW)On-demand SQL over files in the lakeManaged Spark clusters
You pay forData Warehouse Units (DWUs) per hour, can be pausedData processed per TB; nothing when idleNode-hours while the pool runs
Data livesIn the pool's own managed storage, spread over 60 distributionsStays in ADLS (CSV, Parquet, Delta)In ADLS
Best forLarge, predictable, high-concurrency BI on modelled dataExploration, ad hoc queries, logical data warehouse viewsData engineering and ML in Spark

Facts worth remembering

  • Dedicated pool tables pick a distribution: hash for big fact tables, replicated for small dimension tables, round-robin for staging.
  • Pause a dedicated pool at night or at weekends: compute billing stops, and storage is still charged.
  • Synapse Link gives near-real-time analytics over operational data (Cosmos DB, Azure SQL, Dataverse) without building ETL and without loading the source.
Name check

Dedicated SQL pools were previously Azure SQL Data Warehouse. Microsoft's newest analytics investment goes into Microsoft Fabric (see 07.8), and Synapse remains a supported service that the exam still covers. For a new greenfield platform, expect a real conversation about Fabric.

Exam cue

"Enterprise data warehouse", "MPP", "petabyte-scale SQL", "pause compute to save cost" → dedicated SQL pool. "Query Parquet/CSV files in the lake with T-SQL", "no infrastructure", "pay per query" → serverless SQL pool. "Analyse Cosmos DB data without affecting the app" → Synapse Link (or Fabric mirroring).

07.7

Azure Stream Analytics

SQL for data that never stops arriving

Definition

Azure Stream Analytics is a fully managed, real-time analytics and complex event-processing service. A job reads from streaming inputs (such as Event Hubs, IoT Hub or Blob storage), runs a SQL-like query with temporal functions such as windows, and writes results continuously to outputs such as Power BI, Azure SQL, Cosmos DB, Data Lake Storage, Event Hubs or Azure Functions.

In plain words

A normal query asks a question of data that's already sitting still. A Stream Analytics query sits still while the data flows past it, and answers continuously: "every 5 minutes, how many orders per store?", "alert if any freezer reports above −10°C for 2 minutes". If you can write a GROUP BY, you can write one.

A query you can read without knowing Stream Analytics

-- Orders per store, every 5 minutes
SELECT StoreId, COUNT(*) AS Orders, System.Timestamp() AS WindowEnd
INTO   [powerbi-live]
FROM   [orders-eventhub] TIMESTAMP BY EventTime
GROUP BY StoreId, TumblingWindow(minute, 5)

Facts worth remembering

  • Capacity is set in streaming units; scale them up for more events or more complex queries.
  • Reference data (such as a store list from Blob or Azure SQL) can be joined to the stream for lookups.
  • Built-in anomaly detection functions spot spikes and dips without writing an ML model.
  • Jobs can also run on IoT Edge devices, close to the sensors, when the network is unreliable.
  • Event Hubs is usually the front door: it ingests millions of events per second and holds them for Stream Analytics. More on it in Module 10.
Exam cue

"Analyse streaming data in real time with a SQL-like language", "IoT telemetry", "aggregate every N minutes", "real-time dashboard in Power BI" → Stream Analytics. "Count events in fixed, non-overlapping intervals" → tumbling window. "Rolling overlapping windows" → hopping. "Group a user's activity until they go idle" → session. "Ingest millions of events per second" → Event Hubs.

Say: “If you can write GROUP BY, you can write real-time analytics. The window is the only new idea.”

07.8

Where Microsoft Fabric and Purview fit

Microsoft Fabric

Definition

Microsoft Fabric is an end-to-end, software-as-a-service analytics platform. It brings data integration (Data Factory), data engineering (Spark), data warehousing, real-time intelligence, data science and Power BI together on one shared data lake, OneLake, with a single capacity-based billing model.

In plain words

Everything in this module, but as one SaaS product instead of separate Azure resources you wire together. The concepts (pipelines, lakehouse, warehouse, medallion, streaming) are identical. That's why learning them on ADF, ADLS, Databricks and Synapse is never wasted.

Microsoft Purview

Definition

Microsoft Purview is a family of data governance, risk and compliance solutions. For analytics, its Data Map and Unified Catalog scan data sources across Azure, on-premises and other clouds to discover, classify and catalogue data, and show lineage from source to report.

Imagine this

Purview is the library catalogue for your company's data: which shelf a data set sits on, who owns it, whether it contains personal data, and which reports were built from it. Without it, a data lake slowly becomes a godown nobody dares to clean out.

Exam cue

"Discover and catalogue data across the organisation", "data lineage", "classify sensitive data across sources" → Microsoft Purview. "Unified SaaS analytics platform", "OneLake" → Microsoft Fabric.

Portal demoFind Purview and Fabric, and see the same patterns in SaaS form~2 min

Goal: Show where the governance and SaaS pieces live, so learners recognise them later.

  1. Browse to purview.microsoft.com: point at Data Map (scan sources such as your lake) and Unified Catalog (search, classifications, lineage). Don't register sources in class unless an account already exists.
  2. Browse to app.fabric.microsoft.com (a free trial may be offered): point at Data Factory, Data Engineering (lakehouse), Data Warehouse, Real-Time Intelligence and Power BI, all on OneLake.
  3. Back in the Azure portal, search Microsoft Fabric to show where Fabric capacities (F SKUs) are created and billed. Don't create one.

Say: “Same five stages, same medallion, same pipelines. Fabric just puts them under one roof as SaaS.”

07.11

Recap and self-check

Architect's analytics checklist

  • Operational (OLTP) and analytical (OLAP) workloads separated.
  • Batch vs streaming decided per question, based on how fresh the answer must be.
  • A data lake on ADLS Gen2 with bronze, silver and gold layers, and ACLs per layer.
  • Pipelines orchestrated by Data Factory, with the right integration runtime for each source.
  • The processing engine matched to the people: Spark notebooks, SQL, or both.
  • Serving layer chosen for cost: serverless where usage is light, dedicated or capacity where it's heavy.
  • Streaming path designed with Event Hubs and Stream Analytics windows where minutes matter.
  • Governance in place: Purview catalogue, lineage, classification and data residency.

Self-check

1. A nightly pipeline must copy data from an on-premises SQL Server to a data lake in Azure. Which service and which component makes the on-premises connection possible?

Azure Data Factory with a self-hosted integration runtime installed on a machine that can reach the on-premises SQL Server.

2. Analysts want to run T-SQL directly over Parquet files in the lake, occasionally, without provisioning anything. What do you recommend?

The Synapse serverless SQL pool. It queries files in place and charges per TB of data processed.

3. A data science team wants to train ML models on 5 TB of history using Python notebooks, collaboratively. Which service?

Azure Databricks: Spark-based, collaborative notebooks, MLflow, and Delta Lake on ADLS Gen2.

4. Sensors send readings every second. You need the average temperature per device for each fixed, non-overlapping 1-minute interval, shown on a live dashboard. Design?

Event Hubs (or IoT Hub) → Stream Analytics with a tumbling window of 1 minute → Power BI output.

5. A data lake must let the finance team read only the /gold/finance folder. How?

Use ADLS Gen2 (hierarchical namespace) and grant the finance Entra group read and execute ACLs on that directory (plus execute on the parent folders), instead of an RBAC role on the whole account.

6. The company has 300 existing SSIS packages and wants to run them in Azure without rewriting them. What do you use?

An Azure-SSIS integration runtime in Azure Data Factory.
