  • Files, objects and disksIs it a file, an object or a disk?31
    • The container: storage accountOne endpoint, one redundancy choice, one security boundary5
      • Storage accountthe box that holds Blob, Files, Queue, Table

        A named Azure resource that groups Blob, Files, Queue and Table storage under one endpoint, one redundancy setting and one set of network and security rules.

        Use it whenAlways, for Blob, Files, Queue and Table. Standard general-purpose v2 is the default; choose Premium (block blobs, file shares or page blobs) for low latency and high transaction rates.
        Look elsewhere whenYou need VM disks (managed disks are their own resource) or a database engine. Split into separate accounts when data needs different redundancy, region or access rules.
        Exam wordsgeneral-purpose v2premium block bloblow latency, high transactions

        Meridian Separate accounts per purpose and per region; EU accounts in Germany West Central.

        Module 05 · Storage accounts →
      • RedundancyHow many copies, how far apart4
        • LRS3 copies, one datacentre

          Locally redundant storage keeps three synchronous copies inside one datacentre.

          Use it whenCheapest option; data you can recreate; or rules say data must stay in one place.
          Look elsewhere whenThe workload must survive a zone or region outage.
          Exam wordslowest costdata can be recreatedsingle location
          Module 05 · Redundancy →
        • ZRS3 copies across 3 zones

          Zone-redundant storage keeps three synchronous copies across three availability zones in one region.

          Use it whenStay available when a whole datacentre (zone) fails, with no data loss.
          Look elsewhere whenYou need a copy in another region for disaster recovery: use GZRS.
          Exam wordszone outagesynchronoushigh availability in one region

          Meridian HQ file shares on Azure Files with ZRS; the analytics lake with ZRS.

          Module 05 · Redundancy →
        • GRS / RA-GRSLRS here + LRS in the paired region

          Geo-redundant storage adds an asynchronous copy (LRS) in a secondary region. RA- adds a read-only endpoint on the secondary.

          Use it whenSurvive a regional disaster. Pick RA-GRS when apps must still read during the outage.
          Look elsewhere whenYou also need zone protection in the primary region: use GZRS.
          Exam wordsregional disasterpaired regionread from secondary
          Module 05 · Redundancy →
        • GZRS / RA-GZRSZRS here + LRS in the paired region

          Geo-zone-redundant storage: three zones in the primary region plus an asynchronous copy in the secondary. RA-GZRS adds read access to the secondary.

          Use it whenCritical data that needs both zone and region protection. RA-GZRS is the maximum durability and availability option.
          Look elsewhere whenCost matters more than surviving a region loss, or residency rules forbid a second region.
          Exam wordsmaximum durabilityzone and regionread during regional outage

          Meridian Product images: RA-GZRS, Central India with South India as secondary.

          Module 05 · Redundancy →
    • Objects over HTTPImages, video, documents, backups9
      • Blob storageobjects you name with a URL

        Object storage for unstructured data. Block blobs for files and media, append blobs for logs, page blobs for random read/write.

        Use it whenImages, video, documents, backups, exports: anything an app or user fetches over HTTPS.
        Look elsewhere whenUsers need a mapped drive or SMB path (Azure Files), or a VM needs a disk (managed disks).
        Exam wordsunstructured dataobjectsimages and videostatic content

        Meridian Product images in Hot Blob behind Front Door.

        Module 05 · Blob storage →
      • Access tiersPay for storing, or pay for reading5
        • Hotread often, no minimum stay

          Highest storage price, lowest access price, no minimum stay.

          Use it whenData read or changed frequently, such as live product images.
          Look elsewhere whenData that sits untouched for weeks.
          Exam wordsfrequently accessed
          Module 05 · Access tiers →
        • Cool30-day minimum

          Cheaper storage, dearer reads; 30-day minimum stay (early deletion is charged).

          Use it whenData read now and then, kept at least a month: short-term backups, older invoices.
          Look elsewhere whenData read many times a day: access charges outweigh the saving.
          Exam wordsinfrequently accessedat least 30 days
          Module 05 · Access tiers →
        • Cold90-day minimum

          Cheaper again to store, still online; 90-day minimum stay.

          Use it whenRarely read data that must still be available instantly when it is needed.
          Look elsewhere whenData that can wait hours to be read: Archive is cheaper.
          Exam wordsrarely accessedat least 90 daysonline
          Module 05 · Access tiers →
        • Archiveoffline, 180-day minimum

          Cheapest to store, offline; 180-day minimum and hours to rehydrate before you can read it.

          Use it whenCompliance copies and history almost nobody reads.
          Look elsewhere whenAnyone may need the data within minutes.
          Exam wordslong-term retentionrarely if ever readhours to retrieve

          Meridian ~200 TB of old archive shares, shipped by Data Box straight to Archive.

          Module 05 · Access tiers →
        • Lifecycle managementrules that move or delete blobs

          Policies that move blobs between tiers, or delete them, based on age or last access.

          Use it whenData whose value drops with age: the classic "Hot 30 days, then Cool, then Archive, then delete".
          Look elsewhere whenAccess is unpredictable and a wrong move would mean early-deletion or rehydration charges.
          Exam wordsautomatically moveminimise cost over timedelete after N years

          Meridian Invoices: Hot → Cool 30 → Cold 90 → Archive 180 → delete at 7 years.

          Module 05 · Lifecycle →
      • Protecting blobsUndo mistakes, stop tampering3
        • Soft delete and versioningundo deletes and overwrites

          Soft delete keeps deleted blobs and containers for 1–365 days; versioning keeps every previous version on overwrite.

          Use it whenEvery production account: protects against accidental delete or a wrong file uploaded over the right one.
          Look elsewhere whenYou need a copy outside the account or a separate vault: use Azure Backup (Module 08).
          Exam wordsaccidental deletionrestore previous version
          Module 05 · Protecting blobs →
        • Point-in-time restoreroll a container back in time

          Restores a set of block blobs to how they looked at an earlier time. Needs versioning, change feed and soft delete.

          Use it whenA bad batch job or ransomware-style mass change must be undone in one go.
          Look elsewhere whenYou only need single-file recovery: soft delete and versioning are enough.
          Exam wordsrestore to an earlier stateblock blobs
          Module 05 · Protecting blobs →
        • Immutable storage (WORM)nobody can change or delete it

          Time-based retention or legal hold. Once a policy is locked, not even the Owner can shorten it.

          Use it whenRegulated records: audit logs, financial records, legal evidence.
          Look elsewhere whenData must be editable or deletable on request (for example GDPR erasure) during the period.
          Exam wordswrite once, read manyWORMlegal holdcannot be modified

          Meridian Time-based immutability on the audit container.

          Module 05 · Protecting blobs →
      • ↪Data Lake Storage Gen2Blob with folders: see Analyse and serve
    • Shared foldersFile shares and NAS3
      • Azure FilesSMB and NFS shares, managed

        Fully managed file shares over SMB and NFS, mountable by Windows, Linux and macOS, with identity-based access through AD DS, Entra Domain Services or Entra Kerberos.

        Use it whenLift-and-shift file servers, shared team drives, app config shares: no code change.
        Look elsewhere whenApps that talk HTTP (Blob), or very high-performance NAS for SAP or HPC (Azure NetApp Files).
        Exam wordsSMBfile sharelift and shift file servermapped drive

        Meridian ~40 TB HQ shares: Standard, ZRS, AD DS authentication.

        Module 05 · Azure Files →
      • Azure File Synccache the share on local servers

        Syncs Azure file shares to Windows Servers on-premises, with cloud tiering so only hot files stay local.

        Use it whenBranches need local speed while Azure holds the master copy; replacing many small file servers.
        Look elsewhere whenUsers can reach Azure directly with good latency: mount Azure Files alone.
        Exam wordsbranch officescache locallycloud tieringWindows Server

        Meridian File Sync at HQ and at every store server.

        Module 05 · Azure File Sync →
      • Azure NetApp Filesenterprise NAS, sub-millisecond

        A NetApp-powered NFS and SMB file service with very low latency and enterprise features such as snapshots and replication.

        Use it whenSAP HANA, HPC, Oracle on NFS, or migrating NetApp workloads.
        Look elsewhere whenGeneral team shares: Azure Files is simpler and cheaper.
        Exam wordsSAP HANAHPCNFS at high performancesub-millisecond latency
        Module 05 · Choosing storage →
    • Block storageDrives for VMs and clusters7
      • Managed disksthe hard drives of your VMs

        Block storage volumes managed by Azure and attached to VMs. You pick a type and size; Azure handles placement and replication (LRS or ZRS).

        Use it whenAny VM's OS and data disks. Shared disks for clustered workloads.
        Look elsewhere whenMany apps need the same files (Azure Files) or you are consolidating a SAN (Elastic SAN).
        Exam wordsVM diskIOPSthroughput
        Module 05 · Managed disks →
      • Disk typesMatch the disk to the IOPS5
        • Ultra Diskup to 400,000 IOPS

          The fastest disk: sub-millisecond latency, IOPS and throughput adjustable on the fly. Data disks only.

          Use it whenSAP HANA, top-tier databases, transaction-heavy workloads.
          Look elsewhere whenOS disks (not supported) or ordinary production VMs: overkill.
          Exam wordssub-millisecondhighest IOPSSAP HANA
          Module 05 · Disk types →
        • Premium SSD v2set IOPS independently of size

          Up to 80,000 IOPS; you set capacity, IOPS and throughput separately. Data disks only.

          Use it whenProduction SQL Server, Oracle and big-data disks, where you want to pay for performance, not oversized disks.
          Look elsewhere whenOS disks (not supported).
          Exam wordsindependent IOPS and sizeproduction database

          Meridian SQL Server VM data and log disks.

          Module 05 · Disk types →
        • Premium SSDproduction VMs and OS disks

          SSD with performance tied to disk size, up to 20,000 IOPS. Can be an OS disk.

          Use it whenProduction VMs and the OS disks of important servers.
          Look elsewhere whenYou need performance without buying a bigger disk: Premium SSD v2.
          Exam wordsproductionOS diskSLA for single VM
          Module 05 · Disk types →
        • Standard SSDweb servers, dev/test

          Consistent SSD latency at a lower price, up to 6,000 IOPS.

          Use it whenWeb servers, light apps, dev/test.
          Look elsewhere whenDatabases under real load.
          Exam wordsdev/testlight workloads
          Module 05 · Disk types →
        • Standard HDDcheapest, infrequent access

          Spinning-disk performance, up to 2,000 IOPS, lowest cost.

          Use it whenBackups, non-critical and infrequently accessed data.
          Look elsewhere whenAnything latency-sensitive.
          Exam wordslowest costinfrequent access
          Module 05 · Disk types →
      • Azure Elastic SANa SAN in the cloud (iSCSI)

        Block storage delivered as a SAN: volume groups and volumes over iSCSI, shared across many workloads.

        Use it whenConsolidating an on-premises SAN; block volumes for VMs, AKS and Azure VMware Solution from one pool.
        Look elsewhere whenA handful of VMs: managed disks are simpler.
        Exam wordsSANiSCSIconsolidate storage
        Module 05 · Choosing storage →
    • Simple app building blocksBasic queues and key-value tables2
      • Queue storagesimple message queue

        A basic queue for passing small messages between app components, inside a storage account.

        Use it whenSimple decoupling: a web tier drops work items for a background worker.
        Look elsewhere whenYou need ordering, transactions, sessions, topics or duplicate detection: Service Bus (Module 10).
        Exam wordssimple queuedecouple componentslowest cost
        Module 05 · Choosing storage →
      • Table storagecheap key-value table

        A schemaless key-value store addressed by partition key and row key.

        Use it whenCheap, simple lookups at small scale: settings, device metadata.
        Look elsewhere whenGlobal distribution, guaranteed low latency or rich queries: Cosmos DB for Table.
        Exam wordskey-valueschemalesslow cost
        Module 05 · Choosing storage →
    • Getting data inWhen the network is too slow1
      • Azure Data Boxan appliance shipped to you

        A rugged storage device Microsoft ships to you; you copy data locally and ship it back for upload to Blob or Files.

        Use it whenTens to hundreds of terabytes with no fast network, or a one-off bulk move.
        Look elsewhere whenSmall or continuous transfers: AzCopy, File Sync or Data Factory over the network.
        Exam wordsoffline transferlimited bandwidthterabytes

        Meridian ~200 TB of archive shares into Blob Archive.

        Module 05 · Choosing storage →
    • Securing storageThree gates every request passes4
      • Gate 1: networkwho can reach the endpoint

        Firewall rules, service endpoints and private endpoints decide which networks can reach the account.

        Use it whenProduction data: disable public access and use private endpoints.
        Look elsewhere whenPublic content that must be reachable by anyone (serve it through Front Door instead of opening the account).
        Exam wordsprivate endpointdisable public accessselected networks
        Module 05 · Storage security →
      • Gate 2: authorisationEntra RBAC, SAS, keys

        Entra ID + RBAC by default; user delegation SAS for temporary outside access; shared key treated as root.

        Use it whenRBAC with managed identities for apps; user delegation SAS (max 7 days) for partners.
        Look elsewhere whenAccount keys or account SAS in apps: hard to revoke. Disable shared key where you can.
        Exam wordsuser delegation SASmanaged identityStorage Blob Data Readerdisable shared key

        Meridian Shared key disabled; user delegation SAS for partners' proof-of-delivery uploads.

        Module 05 · Storage security →
      • Gate 3: encryptionMicrosoft-managed or your own keys

        Data is always encrypted at rest. Choose Microsoft-managed keys, or customer-managed keys in Key Vault, plus TLS in transit.

        Use it whenCustomer-managed keys when compliance demands you control rotation and revocation.
        Look elsewhere whenNo requirement for key control: Microsoft-managed keys need no work.
        Exam wordscustomer-managed keysKey Vaultminimum TLS

        Meridian CMK for PCI accounts.

        Module 05 · Storage security →
      • Defender for Storagethreats and malware scanning

        Detects unusual access and scans uploaded blobs for malware.

        Use it whenAccounts that accept uploads from outside, such as partner or customer files.
        Exam wordsmalware scanningthreat detection

        Meridian Malware scanning on the partner upload account.

        Module 05 · Storage security →
  • DatabasesDoes it need a database engine?40
    • Relational: the Azure SQL familySame engine, three ways to run it4
      • Azure SQL DatabasePaaS, one database

        Fully managed SQL Server engine for a single database: built-in HA, backups and patching, newest features first.

        Use it whenNew relational apps that want minimal admin and elastic scale.
        Look elsewhere whenYou need SQL Agent, cross-database queries or CLR (Managed Instance), or OS access (SQL VM).
        Exam wordsminimal administrationPaaSnew applicationserverless

        Meridian Orders: Business Critical, zone-redundant, in a failover group.

        Module 06 · Azure SQL family →
      • Elastic poolmany databases share resources

        A pool of vCores or eDTUs shared by many Azure SQL databases whose peaks happen at different times.

        Use it whenSaaS with a database per customer, or many small databases with unpredictable use.
        Look elsewhere whenOne large busy database: size it on its own.
        Exam wordsmany databasesunpredictable usageSaaSminimise cost

        Meridian 180 store inventory databases in elastic pools.

        Module 06 · Scaling →
      • Azure SQL Managed Instancea whole SQL Server instance, managed

        PaaS with near-100% SQL Server compatibility: SQL Agent, cross-database queries, CLR, Service Broker, deployed inside your VNet.

        Use it whenMigrating existing SQL Server estates with minimal change.
        Look elsewhere whenYou need OS access, SSRS/SSAS on the box or an unsupported version (SQL VM).
        Exam wordsSQL Agentcross-database queriesCLRlift and shift SQL Server

        Meridian Merchandising ERP on MI, General Purpose.

        Module 06 · Azure SQL family →
      • SQL Server on Azure VMIaaS, full control

        SQL Server installed on a VM you manage; the SQL IaaS Agent extension adds automated patching and backup.

        Use it whenOS-level access, SSRS/SSAS/SSIS on the same server, or a version PaaS doesn't support.
        Look elsewhere whenNo such constraint: PaaS removes the patching and HA work.
        Exam wordsOS accessfull controlunsupported versionSSRS

        Meridian One vendor app, until the vendor upgrades.

        Module 06 · Azure SQL family →
    • Purchasing models and tiersHow you buy compute and storage5
      • DTU modelsimple bundled sizes

        Basic, Standard and Premium: compute, memory and I/O bundled into Database Transaction Units.

        Use it whenSmall, simple workloads, or estates already on DTU.
        Look elsewhere whenYou want to size compute and storage separately or use Azure Hybrid Benefit: vCore.
        Exam wordssimplebundledBasic / Standard / Premium
        Module 06 · Tiers →
      • General Purpose (vCore)balanced, most apps

        Compute with remote storage; 99.99% SLA.

        Use it whenMost business apps where cost matters.
        Look elsewhere whenLow-latency OLTP or a free read replica is needed: Business Critical.
        Exam wordsbudget-orientedmost workloads
        Module 06 · Tiers →
      • Business Critical (vCore)local SSD, 4 replicas

        Local SSD storage, four replicas, a free read-only replica and in-memory OLTP.

        Use it whenLow-latency OLTP, fastest failover, reporting on the read replica.
        Look elsewhere whenCost-sensitive apps without those needs.
        Exam wordslow latencyread replicain-memory OLTPhighest resilience

        Meridian Orders database; head-office reports on the read replica.

        Module 06 · Tiers →
      • Hyperscale (vCore)up to 128 TB, fast scale

        Separates compute, log service and page servers: up to 128 TB, near-instant backup and restore, up to 30 named replicas.

        Use it whenLarge or fast-growing databases, heavy read scale-out.
        Look elsewhere whenSmall databases where General Purpose fits.
        Exam wordsup to 128 TBrapid scalenamed replicas
        Module 06 · Tiers →
      • Serverless computeauto-scale, per-second billing

        Scales vCores within a range and bills per second; General Purpose serverless can auto-pause when idle.

        Use it whenIntermittent or unpredictable use: dev/test, internal tools, new apps.
        Look elsewhere whenSteady, busy workloads: provisioned is cheaper.
        Exam wordsintermittentauto-pauseunpredictable usage
        Module 06 · Tiers →
    • ScalingUp, out for reads, share, or split3
      • Scale upmore vCores, higher tier

        Give one database more compute or a higher tier; a short reconnect at the switch.

        Use it whenThe whole workload, reads and writes, needs more power.
        Look elsewhere whenOnly reads are heavy: read scale-out is cheaper.
        Exam wordsincrease compute
        Module 06 · Scaling →
      • Read scale-outsend reports to a replica

        Read-only queries (ApplicationIntent=ReadOnly) go to a replica: built into Business Critical, Premium and Hyperscale.

        Use it whenReporting slows down the primary.
        Look elsewhere whenWrites are the bottleneck.
        Exam wordsoffload reportingread-only workload
        Module 06 · Scaling →
      • ↪Elastic poolshare resources across databases
      • Shardingsplit the data across databases

        Partition data across several databases, for example by tenant or region.

        Use it whenData too large or busy for one database even at the top tier.
        Look elsewhere whenAny simpler option fits: sharding puts work on the application.
        Exam wordspartition by tenanthorizontal scale
        Module 06 · Scaling →
    • Availability and recoveryReplicas survive outages; backups undo mistakes6
      • Zone redundancysurvive a zone failure

        Spreads replicas across availability zones. A setting on General Purpose, Business Critical and Hyperscale.

        Use it whenProduction databases in regions with zones; up to 99.995% SLA on Business Critical.
        Look elsewhere whenRegion loss: add geo-replication or a failover group.
        Exam wordszone outage99.995%
        Module 06 · Availability →
      • Active geo-replicationreadable secondaries, per database

        SQL Database only: up to four readable secondaries in any region, failed over database by database.

        Use it whenPer-database DR or readable copies near distant users.
        Look elsewhere whenMany databases must fail over together with unchanged connection strings: failover groups.
        Exam wordsreadable secondaryper database
        Module 06 · Availability →
      • Failover groupsfail over together, same names

        A group of databases (SQL Database or Managed Instance) that fails over together behind listener names that never change.

        Use it whenRegion-level DR for an application, the default answer in most designs.
        Look elsewhere whenYou only need protection from mistakes: that's backups.
        Exam wordsautomatic failoversame connection stringgroup of databasesManaged Instance DR

        Meridian Orders: Central India ↔ South India; ERP on MI in its own group.

        Module 06 · Failover groups →
      • Point-in-time restoreundo mistakes, 1–35 days

        Automatic backups; restore to any point in the last 1–35 days (7 by default) as a new database.

        Use it whenBad deployments, accidental deletes, corruption: replicas copy mistakes, backups undo them.
        Look elsewhere whenRetention beyond 35 days: long-term retention.
        Exam wordsrestore to a point in timeaccidental delete

        Meridian 35 days on orders.

        Module 06 · Availability →
      • Long-term retentionweekly, monthly, yearly for up to 10 years

        Keeps full backups weekly, monthly or yearly for up to 10 years.

        Use it whenCompliance and audit retention.
        Look elsewhere whenFast recovery from today's mistake: PITR.
        Exam wordscompliancekeep backups for years

        Meridian Yearly backups for 7 years.

        Module 06 · Availability →
      • Geo-restorecheapest regional recovery

        Restore from geo-replicated backups into any region.

        Use it whenDR where hours of downtime and some data loss are acceptable, at no extra cost.
        Look elsewhere whenLow RTO/RPO: failover groups.
        Exam wordslowest cost DRhours of RTO
        Module 06 · Availability →
    • Protecting dataAt rest, in transit, in use6
      • Transparent Data Encryptionencrypt files, logs and backups

        Encrypts data files, logs and backups in real time, invisible to apps; on by default. Customer-managed keys let you revoke access.

        Use it whenAlways. Use CMK when you must control the key.
        Look elsewhere whenHiding data from DBAs or admins: that's Always Encrypted.
        Exam wordsencryption at restcustomer-managed keyBYOK

        Meridian TDE with CMK in Key Vault.

        Module 06 · Protecting data →
      • Always Encryptedeven the DBA can't read it

        Columns are encrypted in the client driver; keys stay in Key Vault, outside the database.

        Use it whenSensitive columns (national ID, card data, phone) that admins must never see.
        Look elsewhere whenRich queries over the column without secure enclaves.
        Exam wordsprotect from administratorsclient-side encryptiondata in use

        Meridian Customer phone and address columns.

        Module 06 · Protecting data →
      • Dynamic data maskingshow XXXX-1234

        Masks values in query results for users without UNMASK. Presentation only: the data is unchanged.

        Use it whenSupport staff need to see a record, not the full sensitive value.
        Look elsewhere whenYou need real protection from a determined user: encrypt instead.
        Exam wordsmasklimit exposuresupport staff
        Module 06 · Protecting data →
      • Row-level securityeach user sees only their rows

        A predicate decides which rows each user can see.

        Use it whenMulti-tenant or per-region data in one table: "store managers see only their store".
        Look elsewhere whenColumn-level hiding: masking or encryption.
        Exam wordsrestrict rowsper tenantper user
        Module 06 · Protecting data →
      • Entra authenticationno SQL passwords

        Users, groups and managed identities sign in with Entra ID; Entra-only authentication turns SQL logins off.

        Use it whenEvery new design: MFA, Conditional Access, no passwords in config.
        Exam wordsmanaged identityEntra-onlyno passwords
        Module 06 · Protecting data →
      • Auditing, Defender, ledgerwho did what, threats, tamper evidence

        Auditing records activity; Defender for SQL finds vulnerabilities and SQL injection; ledger makes tampering evident.

        Use it whenRegulated data and anything internet-facing.
        Exam wordsauditSQL injectiontamper-evident

        Meridian Auditing to law-central-ind, Defender for SQL.

    • Relational: open sourcePostgreSQL and MySQL, managed3

        Use it whenExisting PostgreSQL apps or teams that prefer the open-source engine.
        Look elsewhere whenSQL Server features or T-SQL code: Azure SQL.

Mindset takeaway

On an exam question, read the requirement words first and pick the top branch (what shape is the data, what job is being done). Then the middle branch (access pattern, engine, batch or stream). Only then the leaf, and finally the settings under it: tier, redundancy, consistency. Most wrong answers are a right service on the wrong branch.
