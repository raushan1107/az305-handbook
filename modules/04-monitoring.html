04.1

Why monitoring is architecture, not an afterthought

Imagine this

A hospital ICU. The heart-rate monitor beeps constantly with numbers (metrics). The patient's file has detailed notes: what was given, when, by whom, and what happened (logs). The alarm calls the nurse when a number crosses a line (alerts). And the doctor's weekly review spots slow trends no single beep would show (workbooks and analytics). Remove any one of these and patients get hurt, even with the best doctors.

Developer view

"I'll add logging when there's a bug. For now, Console.WriteLine is fine."

Architect view

"Monitoring is how we prove the SLO from Module 01, detect failures before customers do, audit the identity controls from Module 03, and control cost. It's designed in, with an owner, a budget and a retention policy."

Mindset takeaway

Your monitoring design should answer four questions without anyone logging in to a server: Is it up? Is it fast? Is it secure? What did it cost?

04.2

Azure Monitor and its data sources

One platform, many signals

Definition

Azure Monitor is a comprehensive monitoring solution for collecting, analysing and responding to telemetry from cloud and on-premises environments. It stores data as metrics and logs, and provides the tools to query, visualise and alert on it.

In plain words

Azure Monitor isn't one tool. It's the umbrella name for the whole pipeline in the mental map. Log Analytics, Application Insights, alerts and Workbooks are all parts of Azure Monitor. That trips people up in the exam.

The layers of data, from code to tenant

LayerWhat you getCollected byOn by default?

Guest OSWindows events, Syslog, performance counters inside the VMAzure Monitor Agent + data collection ruleNo, install the agent
Azure resourcePlatform metrics (automatic) and resource logs (e.g. Key Vault reads, SQL audit)Metrics: automatic. Resource logs: diagnostic settingsMetrics yes; resource logs no
SubscriptionActivity log: control-plane changes, service health eventsAutomatic (90 days); diagnostic setting to keep longerYes, 90 days
TenantEntra sign-in logs, audit logsEntra diagnostic settingsKept in the portal for 7 days (Free) or 30 days (P1/P2); route to a workspace to keep longer
Common trap

Resource logs are not collected until you create a diagnostic setting. Many teams discover this during their first security incident, when they go looking for "who read that secret?" in Key Vault and find nothing was ever recorded. Use Azure Policy (DeployIfNotExists, from Module 02) to switch them on everywhere automatically.

04.4

Collecting and routing data

Diagnostic settings

Definition

A diagnostic setting specifies which categories of resource logs, activity log or platform metrics to collect from a resource, subscription or tenant, and which destinations to send them to.

You can create up to five diagnostic settings per resource, each with different categories and destinations. The architect's question is always: what will this data be used for? That decides where it goes.

Azure Monitor Agent and data collection rules

Definition

The Azure Monitor Agent (AMA) collects monitoring data from the guest operating system of Azure and hybrid machines. What it collects and where it sends the data is defined centrally in data collection rules (DCRs).

  • AMA replaces the legacy Log Analytics agent (MMA/OMS), which was retired in August 2024. If an answer mentions installing the legacy agent for a new design, that's a red flag.
  • One DCR can apply to many machines; one machine can have several DCRs (e.g. a security team rule and an operations team rule).
  • DCRs can filter and transform data before it's stored, which is one of the best ways to cut ingestion cost.
  • For on-premises or other-cloud servers, onboard them with Azure Arc, then use the same AMA + DCR approach.
Exam cue

"Collect Windows event logs / performance counters from VMs", "on-premises servers into the same workspace", "collect only specific events to reduce cost" → Azure Monitor Agent + data collection rules (+ Azure Arc for non-Azure machines).

04.5

Log Analytics workspaces

Where your logs live, and the most important design decision in this module

Definition

A Log Analytics workspace is a unique environment for log data from Azure Monitor and other Azure services such as Microsoft Sentinel and Defender for Cloud. Each workspace has its own data repository, region, configuration, retention and access control, and is queried with Kusto Query Language (KQL).

KQL in plain words

KQL (Kusto Query Language) is a read-only query language designed for logs and time-series data — think of it as SQL for logs. You name a table, then pipe it through a chain of operations: AzureActivity | where Level == "Error" | summarize count() by ResourceGroup. The table comes first, steps are joined by |, and you never write UPDATE or DELETE. If you can read SQL, KQL will feel familiar within minutes.

Imagine this

A workspace is a library building. It stands in one city (region), has its own membership rules (access), its own policy on how long books are kept (retention), and its own running costs (billing). You can build one big central library or several branch libraries. Neither is wrong; it depends on who needs to read what, and where the books are legally allowed to be.

One workspace or many?

Microsoft's guidance is to start with as few workspaces as possible, ideally one, and add more only for a clear reason. A single workspace makes cross-resource queries, correlation and cost management much simpler.

Design decisions inside a workspace

Access control modeResource-context lets people query logs only for resources they have access to, without workspace-wide rights. Table-level RBAC restricts sensitive tables (e.g. security events).
RetentionInteractive (queryable) retention defaults to 30 days and can be extended to 2 years. Long-term retention keeps data cheaply for up to 12 years, with search jobs or restore to bring it back.
Table plansAnalytics for full query and alerting. Basic and Auxiliary for high-volume, rarely-queried logs at a much lower price, with limited query features.
Cost controlsCommitment tiers discount predictable daily volumes. A daily cap stops runaway cost (but drops data). DCR transformations filter noise before it's billed.
Exam cue

"Logs must stay in the EU" → a workspace in an EU region. "Application teams must see only their own resources' logs" → resource-context access, not separate workspaces. "Retain audit logs for 7 years at minimum cost" → long-term retention in the workspace, or archive to a storage account if they never need querying. "Verbose debug logs, rarely queried" → Basic or Auxiliary table plan.

Portal demoExplore the workspace and run your first KQL~5 min

  • If a table is empty, it's usually ingestion delay (minutes) or a missing diagnostic setting. Both are worth saying out loud.

Say: “Last module this question had no answer. Now it's three lines of KQL.”

04.6

Application Insights

Definition

Application Insights is the application performance monitoring (APM) feature of Azure Monitor. It collects requests, dependencies, exceptions, traces and custom telemetry from live applications, and stores them in a Log Analytics workspace.

In plain words

Infrastructure monitoring says "the server is fine". Application Insights says "but checkout calls to the payment API are taking 4 seconds since the 11:20 deployment, and 3% of them fail with a timeout". It looks at your system the way a customer experiences it.

Application mapAuto-drawn picture of your components and their dependencies, with failure rates on each arrow.
Distributed tracingFollows one request across services, so you see exactly where the time went.
Availability testsSynthetic checks that ping your URL from multiple global locations, so you know before users do.
OpenTelemetryThe vendor-neutral standard for instrumentation; the Azure Monitor OpenTelemetry distro is the recommended way to instrument new apps.

All Application Insights resources are now workspace-based: the telemetry lands in a Log Analytics workspace, so you can join application data with infrastructure and security logs in one KQL query.

Exam cue

"Monitor response times / failure rates of a web app", "identify slow dependencies", "track user behaviour and page views", "test availability from multiple regions" → Application Insights.

04.7

Alerts and action groups

Definition

Azure Monitor alerts proactively notify you when a condition is found in your monitoring data. An alert rule defines the scope, signal and condition. An action group defines who to notify and which automated actions to run.

Alert typeBest forExample
Metric alertFast, numeric conditions; near real-timeAverage CPU > 80% for 10 minutes
Log search alertComplex conditions across records or resourcesMore than 5 failed Key Vault reads by one caller in 5 minutes
Activity log alertControl-plane eventsSomeone deleted a resource group, or a policy assignment changed
Service health alertAzure-side incidents and planned maintenance in your regionsAzure SQL degradation in Central India
Resource health alertHealth of your specific resource instanceThis VM became unavailable
The beginner's alerting

An email for every warning to a shared mailbox. Within a month there are 400 unread alerts and nobody looks any more.

Architect view

Alert on symptoms customers feel (error rate, latency, availability), not every cause. Use severity to separate "wake someone up" from "look tomorrow". Use dynamic thresholds where "normal" varies. Automate the known fixes. Every alert must have an owner and a runbook.

Exam cue

"Notify the team and run a script when…" → one alert rule with an action group containing both. "Be notified of Azure platform issues affecting your resources" → Service Health alerts. "Suppress alerts during planned maintenance" → alert processing rules. "Know when someone deletes a resource" → activity log alert.

04.9

Azure Data Explorer

When telemetry becomes big data

Definition

Azure Data Explorer (ADX) is a fully managed, high-performance analytics platform for large volumes of streaming data such as logs, telemetry and time series. It's queried with KQL, the same language as Log Analytics, and delivers interactive results across billions of records.

In plain words

Log Analytics is actually built on the same engine. ADX hands you the engine itself, so you control the cluster, the schema, the ingestion and the cost model. You pick it when you have your own massive telemetry problem, not just "monitor my Azure resources".

Log AnalyticsAzure Data Explorer
PurposeOperational monitoring of Azure and hybrid resourcesCustom big-data analytics on telemetry, IoT, clickstream, time series
ManagementFully managed SaaS-like; no cluster to sizeYou size and manage a cluster (or use a free/serverless option)
IntegrationBuilt into alerts, Insights, Sentinel, DefenderIngest from Event Hubs, IoT Hub, storage; visualise in dashboards, Grafana, Power BI
Data shapePredefined Azure Monitor tables (plus custom)Your own schema, your own retention and caching policy
Choose when"Monitor our Azure environment""Analyse terabytes of device telemetry per day, interactively, for years"
Related

The same Kusto engine also powers Eventhouse in Microsoft Fabric's Real-Time Intelligence. For AZ-305, keep ADX as the Azure answer for "large-scale, near real-time analytics over log and telemetry data with KQL".

Exam cue

"Analyse IoT/telemetry data at very high volume", "time-series analysis", "ad hoc queries over billions of rows in seconds", "KQL but outside Azure Monitor" → Azure Data Explorer.

04.12

Recap and self-check

Architect's monitoring checklist

  • Workspace strategy decided: as few as possible, split only for residency, billing or isolation.
  • Diagnostic settings enforced by Policy for resources, the activity log and Entra ID.
  • VMs and hybrid servers on Azure Monitor Agent with data collection rules.
  • Application Insights with availability tests on every customer-facing app.
  • Alerts on customer-facing symptoms, with severity, owners, action groups and runbooks.
  • Retention and table plans set per data type; long-term retention for compliance.
  • Access to logs follows least privilege (resource-context, table-level RBAC).
  • Monitoring cost has a budget and a monthly review.

Self-check

1. Security asks "who read the payment API secret last Tuesday?" and there's no data. What was missing?

A diagnostic setting on the Key Vault sending its AuditEvent logs to a Log Analytics workspace. Resource logs aren't collected by default. Enforce them with Azure Policy (DeployIfNotExists).

2. Logs must be queryable for 90 days and retained for 7 years for compliance, at minimum cost. Design?

Set interactive retention to 90 days and total retention to 7 years (long-term retention) on the relevant tables. Alternatively, also route to a storage account with lifecycle management (and immutability if required) when the archive will almost never be queried.

3. You need to forward Azure resource logs to an existing third-party SIEM. Which diagnostic setting destination?

Event Hubs. It's designed for streaming to external systems. (If the SIEM is Microsoft Sentinel, send to a Log Analytics workspace instead.)

4. Three business units want "their own" monitoring. Do you create three workspaces?

Not by default. Use one workspace with resource-context access so each unit sees only its own resources' logs. Create separate workspaces only for real requirements like data residency, separate billing or different retention.

5. An IoT platform produces 5 TB of telemetry per day that analysts query interactively with complex time-series functions. Log Analytics or ADX?

Azure Data Explorer. It's custom big-data telemetry analytics with your own schema, cluster and cost model, not operational monitoring of Azure resources.

6. How do you get notified when Azure itself has an incident affecting your region's SQL databases?

Create a Service Health alert scoped to your subscriptions, the SQL Database service and your regions, linked to an action group.
