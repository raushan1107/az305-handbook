10.0

The mental map

A modern application is a set of services that talk. They talk in three ways: a client calls an API and waits; a service sends a message that someone must process; a service announces an event that anyone may react to. Around those conversations sit a front door for APIs, a cache for speed, a place for settings, and code that deploys it all.

10.1

Why loose coupling matters

Imagine this

A busy dosa restaurant. If each waiter walked into the kitchen and stood next to the cook until his dosa was ready, six waiters would be stuck in the kitchen and nobody would be taking orders. Instead the waiter pins the order slip on the rail and goes back to the tables. Cooks pick slips in order, at their own speed. When the rush comes, the rail gets longer, nothing breaks, and the manager can add a cook. That rail is a queue.

Developer view

"The order service just calls the payment, stock and email APIs one after the other. It's simple and it works on my machine."

Architect view

"Four synchronous calls means four SLAs multiplied together (Module 01's composite SLA) and the slowest one sets the response time. I keep the call only where the user must wait for the answer (payment), and turn the rest into messages and events."

Mindset takeaway

Ask of every arrow in a diagram: does the caller really need to wait for the answer? If not, it shouldn't be a call.

10.2

Messages, events and patterns

Azure's own guidance draws one line that answers most exam questions: is the sender handing over a job, or announcing a fact?

Message (a command)

"Process this order." The sender expects it to be handled, exactly once, by someone. The message carries the data. If nobody processes it, that's a problem. Think courier parcel: it must reach a person and be signed for.

Event (a fact)

"An order was placed." The publisher doesn't care who listens, or whether anyone does. Lightweight; often just a pointer to the data. Think a society notice board: whoever is interested reads it.

KindExampleAzure service
Message / command"Charge this card", "generate this invoice"Service Bus (enterprise) or Queue Storage (simple)
Discrete event"A blob was created", "a VM was deleted", "order 1234 shipped"Event Grid
Event streamClickstream, POS telemetry, IoT readings: millions per minute, analysed over timeEvent Hubs

Patterns you'll see in questions

Queue-based load levellingA queue absorbs spikes so a backend processes at a steady rate. The rail on the dosa counter.
Competing consumersSeveral workers read the same queue; each message goes to one of them. Add workers to go faster.
Publish / subscribeOne message or event, many independent subscribers, each getting its own copy. Service Bus topics, Event Grid.
Retry and circuit breakerRetry transient failures with back-off; stop calling a failing service for a while so it can recover.
Dead-letter queueMessages that can't be processed after N tries (often a poison message: bad data that fails every time) are parked for a human to inspect, instead of blocking the line.
Idempotent handlerProcessing the same message twice gives the same result as once (for example "set stock to 5", not "subtract 1"). Needed because most queues deliver at least once.
Cache-asideRead from the cache; on a miss, read the database and put the result in the cache for next time.
Exam cue

"The sender expects the work to be done", "order processing", "transactions" → a message (Service Bus). "React to a change", "notify subscribers", "lightweight notification" → a discrete event (Event Grid). "Telemetry", "millions of events", "streaming" → an event stream (Event Hubs).

10.3

Azure Queue Storage

The simplest queue there is

Definition

Azure Queue Storage is a service, part of an Azure storage account, for storing large numbers of messages that can be accessed from anywhere via authenticated HTTP or HTTPS calls. A message can be up to 64 KB, and a queue can hold millions of messages up to the capacity of the storage account.

In plain words

A cheap, huge to-do list inside your storage account. Put messages in, workers take them out. No ordering guarantee, no topics, no transactions. If that's all you need, nothing is cheaper or simpler.

  • Messages are hidden while a worker processes them (visibility timeout) and reappear if the worker crashes: at-least-once delivery. A message can therefore arrive twice, so the worker must be safe to run twice on the same message (idempotent).
  • Default time-to-live is 7 days (configurable, including never expire).
  • Pick it when you need a backlog of more than 80 GB, want progress tracking on a message, or need server-side logs of every transaction.
Exam cue

"Simple queue", "lowest cost", "more than 80 GB of messages", "messages up to 64 KB", "already using a storage account" → Queue Storage. Anything about FIFO, sessions, duplicate detection, topics or transactions → Service Bus.

10.4

Azure Service Bus

Enterprise messaging: queues and topics

Definition

Azure Service Bus is a fully managed enterprise message broker with queues (point-to-point) and publish-subscribe topics. It supports ordered delivery with sessions, duplicate detection, dead-letter queues, scheduled and deferred messages, transactions, and the AMQP 1.0 protocol, so applications and services can be decoupled reliably.

In plain words

A registered post office for business messages. It guarantees delivery, can keep things in order, refuses duplicates, sets aside letters that can't be delivered, and with topics can send copies to several departments at once, each department seeing only the letters its filter allows.

TierKey featuresUse it for
BasicQueues onlySimple, low-cost queueing
StandardQueues and topics, sessions, transactions, messages up to 256 KB; pay per operationMost applications, dev/test
PremiumDedicated capacity (messaging units), predictable latency, messages up to 100 MB, private endpoints, availability zones, geo-disaster recovery and geo-replicationProduction with high throughput, isolation or network requirements
Exam cue

"FIFO / guaranteed order" → Service Bus sessions. "Ignore duplicate messages" → duplicate detection. "Several systems each get a copy", "filter by property" → topics and subscriptions. "Poison messages" → dead-letter queue. "Private endpoint", "predictable performance", "large messages" → Premium.

10.5

Azure Event Grid

"Something happened", pushed to whoever cares

Definition

Azure Event Grid is a fully managed publish-subscribe service that routes events (such as "a blob was created") from Azure services or your own apps to subscribers. It filters each event and pushes it to handlers such as Functions, webhooks or queues, with retries and dead-lettering.

In plain words

Event Grid is the society WhatsApp group for Azure. "A file was uploaded." "A VM was deleted." "A key in Key Vault is about to expire." You don't poll every few seconds asking "anything new?": Event Grid tells you within moments, and only about the things your filter cares about.

Facts worth remembering

  • System topics carry events from Azure services (Storage, resource groups, Key Vault…); custom topics carry your own app's events.
  • An event subscription picks the events (by type and subject filters) and the handler that receives them.
  • Events use the Event Grid schema or the open CloudEvents standard, up to 1 MB each.
  • Failed deliveries are retried for up to 24 hours, then dead-lettered to storage if you configured it.
  • Namespaces add an MQTT broker for devices and pull delivery for apps that prefer to fetch events.
Exam cue

"React when a blob is created", "notify when a resource changes", "event-driven, serverless", "avoid polling", "push to many handlers with filters" → Event Grid. "MQTT from devices" → Event Grid namespaces (MQTT broker).

Portal demoUpload a blob and watch Event Grid drop a notification into a queue~4 min

Goal: Show push-based eventing from an Azure service with no code at all.

  1. Storage account staz305m10… › Containers › + Container: images. Then Queues › + Queue: image-events.
  2. Storage account › Events › + Event Subscription: name on-image-upload, schema Event Grid Schema, system topic name egst-az305-m10; event types: only Blob Created; endpoint type Storage Queues › select image-events.

Say: “Nobody polled. The storage account announced it, and only the subscriber who cared about .jpg heard it.”

10.6

Azure Event Hubs

A firehose of events, kept in order per partition

Definition

Azure Event Hubs is a fully managed, real-time data streaming platform that can ingest millions of events per second. Events are appended to partitions (ordered logs) and retained for a configured period, so many consumer groups can read the same stream independently, at their own pace, and replay it. It offers an Apache Kafka-compatible endpoint and Capture to write the stream to Blob Storage or Data Lake automatically.

In plain words

Event Hubs is not a to-do list; it's a CCTV recording. Every event is written to the tape in order. Security watches it live, the analytics team rewinds to 9 a.m., and nobody's viewing removes anything from the tape. Events expire only when the retention period ends.

Facts worth remembering

  • Partitions decide parallelism: events with the same partition key stay in order. Plan the count up front (it can't be reduced, and only grows on Premium and Dedicated).
  • Consumer groups are independent views of the stream: Stream Analytics in one, a Databricks job in another (Module 07).
  • Tiers: Basic, Standard (Kafka, Capture), Premium and Dedicated (isolation, longer retention up to 90 days, more partitions).
  • Capture lands raw events as Avro or Parquet files in the lake: the bronze layer for free.
Exam cue

"Millions of events per second", "telemetry", "clickstream", "big data streaming", "Kafka without managing Kafka", "replay events", "multiple readers of the same stream" → Event Hubs. "Archive the stream to the lake automatically" → Event Hubs Capture. Device management and cloud-to-device commands for IoT → IoT Hub.

Portal demoSee partitions, consumer groups and Capture on an event hub~3 min

Goal: Connect the CCTV-tape idea to the screens that define a stream.

  1. Search Event Hubs › + Create: namespace evh-az305-m10 + initials, Central India, tier Standard, throughput units 1 › Create.
  2. Open it › + Event Hub: name pos-telemetry, partition count 4, retention (hours or days). Capture tab: show Capture On, output Avro or Parquet to a storage account, time and size windows. Leave it off › Create.

Say: “It's a tape, not a to-do list. Every team rewinds it independently.”

10.8

Azure API Management

One front door for all your APIs

Definition

Azure API Management (APIM) is a hybrid, multicloud platform for managing APIs. It has three parts: the API gateway, which accepts calls, enforces policies (authentication, rate limits, quotas, caching, transformation) and routes to back ends; the management plane, for defining APIs, products and policies; and the developer portal, where consumers discover APIs, read documentation and get subscription keys.

In plain words

APIM is the reception desk of an office building. Visitors (API callers) don't wander the floors; they show ID at reception, get a visitor pass with limits ("max 100 visits a minute"), and are sent to the right department. Departments can move floors without telling visitors. And there's a brochure stand (the developer portal) explaining what each department does.

TierNotes
ConsumptionServerless, pay per call, scales automatically; fewer features. Good for light or spiky APIs.
DeveloperAll features, no SLA. For development and evaluation only.
Basic / Standard (classic and v2)Production with an SLA. The v2 tiers deploy faster and Standard v2 can reach back ends in a VNet.
Premium (classic and v2)Multi-region gateways (classic), VNet injection, availability zones, self-hosted gateways, highest scale.
Exam cue

"Publish APIs to partners", "developer portal", "rate limiting / throttling", "validate JWT", "transform SOAP to REST", "version APIs", "one endpoint for many back ends" → API Management. "Gateway on-premises or in another cloud" → self-hosted gateway. "Multi-region gateway", "internal VNet" → Premium. "Pay per call", "serverless" → Consumption.

10.9

Caching with Redis

Answers kept within arm's reach

Definition

Azure Managed Redis is a fully managed, in-memory data store based on Redis Enterprise software, used as a distributed cache, session store, message broker and for data structures such as sorted sets and streams. It offers Memory Optimized, Balanced, Compute Optimized and Flash Optimized tiers, high availability across zones, persistence and active geo-replication.

Imagine this

A chaiwala doesn't boil fresh milk for every cup. He keeps a pot on the stove for the next twenty cups, and only goes back to the fridge when the pot is empty. Redis is the pot; the database is the fridge. Most requests are served from the pot in under a millisecond.

  • Cache-aside is the default pattern: read cache; on a miss, read the database and write the result to the cache with an expiry (TTL).
  • Session state in Redis makes web servers stateless, so they can scale out and in (Module 09).
  • Also used for leaderboards (sorted sets), rate limiting counters and short-lived locks.
  • The hard part is invalidation: decide how stale data may be, and set TTLs accordingly.
Name check

Azure Cache for Redis is being retired in favour of Azure Managed Redis: the Enterprise tiers in March 2027, and Basic, Standard and Premium on 30 September 2028. Older questions may say "Azure Cache for Redis"; the answer pattern (cache-aside, sessions, sub-millisecond reads) is the same.

Exam cue

"Reduce database load", "sub-millisecond reads", "frequently read, rarely changed data", "store session state for a web farm" → Redis (Azure Managed Redis). "Cache API responses at the gateway" → APIM caching policy. "Cache static content near users" → Front Door (Module 11).

Portal demoWalk the Azure Managed Redis form: tiers, zones and geo-replication~2 min

  2. Show high availability (zones), Networking (private endpoint), and Advanced: clustering policy, active geo-replication, persistence. Cancel.

Say: “The pot of chai on the stove: sized for the rush, and refilled from the fridge only when it's empty.”

10.11

Automated deployment

Infrastructure you can review, repeat and roll back

Definition

Infrastructure as code (IaC) describes resources in declarative files that are version-controlled and deployed by a pipeline. On Azure the native options are ARM templates (JSON) and Bicep (a simpler language that compiles to ARM); Terraform is the common multicloud option. Template specs store approved templates as Azure resources, and deployment stacks manage a set of resources as one unit, with deny settings and clean-up of resources removed from the template.

In plain words

If a resource was built by clicking in the portal, it can only be rebuilt by someone remembering the clicks. Written as Bicep, it's reviewed like code, deployed the same way to dev, test and prod, and rebuilt in another region in minutes. That's also your fastest disaster recovery for the infrastructure (Module 08).

ToolPick it when
BicepAzure-only estate; day-one support for new Azure features; no state file to manage
ARM templatesExisting JSON templates; anything Bicep compiles to
TerraformMulticloud, or a team that already uses it; needs a state file stored safely (for example in a storage account)
Template specsA platform team shares approved, versioned templates with RBAC
Deployment stacksManage a group of resources as one unit; deny manual changes; delete resources removed from the template. The successor to Blueprints' locking idea
Developer view

"I'll create the resources in the portal now and write the templates later."

Architect view

"'Later' never comes, and the portal-built prod never matches test. The pipeline deploys with its own managed identity; humans get Reader in prod. Drift is a bug."

Exam cue

"Repeatable, consistent deployments", "declarative", "Azure-native" → Bicep / ARM. "Multicloud" → Terraform. "Share approved templates across the organisation" → template specs. "Prevent changes to deployed resources", "replace Blueprints" → deployment stacks (with template specs).

Portal demoExport a resource group as a template, and find template specs and deployment stacks~4 min

  1. Open rg-az305-m10-demo › Export template (under Automation): the ARM JSON for everything in the group. Switch to the Bicep tab if shown, and point at the Download option.
  2. Open any resource's create form, fill it, and on Review + create click Download a template for automation: the form becomes a template.
  3. Search Template specs › + Create: name, version 1.0, and the template editor. This is how a platform team shares approved templates with RBAC. Cancel.
  4. Search Deployment stacks (or open a resource group › Deployment stacks): show the create options Action on unmanage (detach or delete) and Deny settings (deny delete, deny write). Cancel.

Point out while you are there

  • The exported template is a starting point, not production IaC: it's verbose and hard-codes names. Real templates are written and reviewed.

Say: “If it was built by clicking, it can only be rebuilt by remembering. Write it down as code.”

Recap and self-check

Architect's application checklist

  • Every synchronous call justified: the caller truly needs the answer now.
  • Commands on queues (Service Bus or Queue Storage), facts as events (Event Grid), streams on Event Hubs.
  • Ordering, duplicates and poison messages handled (sessions, duplicate detection, dead-letter).
  • APIs exposed through API Management with authentication, limits and versions.
  • Hot reads cached with a TTL; session state out of the web servers.
  • Settings and feature flags in App Configuration; secrets in Key Vault; access by managed identity.
  • All infrastructure in Bicep or Terraform, deployed by a pipeline, with drift prevented.

Self-check

1. Orders must be processed exactly in the order they were placed for each customer, and duplicates must be ignored. Which service and features?

Service Bus with sessions (session ID = customer ID) for FIFO per customer, and duplicate detection.

2. A Function must run whenever a new image is uploaded to Blob Storage, without polling. Which service delivers the notification?

Event Grid (a system topic on the storage account with a BlobCreated subscription) pushing to the Function.

3. 50,000 sensors send readings every second. Several teams must read the same stream independently, and data must also land in the data lake. Design?

Event Hubs with a consumer group per team, and Capture to ADLS Gen2.

4. A company wants to publish APIs to partners with a self-service portal, per-partner rate limits and token validation. Which service?

Azure API Management: developer portal, products and subscriptions, rate-limit and validate-jwt policies.

5. A web farm loses user sessions every time it scales in. What do you change?

Move session state to a distributed cache, Azure Managed Redis, so instances are stateless.

6. The platform team wants approved templates shared across subscriptions, and resources they deploy protected from manual changes. What do you use?

Template specs to share versioned templates, and deployment stacks with deny settings to protect the deployed resources.
