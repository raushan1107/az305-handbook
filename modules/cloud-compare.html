Cross-Cloud Map: Azure, AWS and Google Cloud Side by Side

You've built on S3 for five years and now the design review is on Azure. Or you know Azure well and the client runs on Google Cloud. This page takes every service in the handbook and puts its AWS and Google Cloud counterpart in the same row, with how close the match really is and what changes when you cross. One job per row, so you compare and don't have to translate in your head.

X.0

How to read this page

In plain words

Each row is one job an architect needs done ("copies in another region", "app identity with no secret"). The three clouds answer it side by side. The last column tells you what trips people up when they move between clouds.

Imagine this

Mumbai local, Delhi Metro and Namma Metro in Bengaluru. Different cards, different line colours, different station names, but "interchange", "last train" and "platform" mean the same thing everywhere. Once you know the job, you only need the local name. A few things really are different, though, like a ladies' coach in one city and not in another. Those are the rows marked Different model.

Same idea Rename it and your design still holds. Close match Same goal; limits, packaging or defaults differ. Different model No one-to-one match, or it behaves differently. Re-think, don't rename.
Exam cue

AZ-305 asks only about Azure. Use this page to translate what you already know, then answer with the Azure service and the exam keywords from its module. Each Azure entry links back to the module that teaches it.

The big differences first

Two pictures explain most cross-cloud confusion. The first is how each cloud organises accounts and where guardrails attach. The second is how far a network and a subnet reach.

Developer view

"S3 is Blob, Lambda is Functions, done." A name lookup is enough to write code against a new cloud.

Architect view

The names map easily; the models don't. Where identity lives, how far a subnet reaches, whether a rule can deny and what the default redundancy is change the design, not just the labels.

X.18

Traps when you cross clouds

  • Subnets and zones. On AWS, one subnet per Availability Zone. On Azure, one subnet covers all zones. On Google Cloud, one VPC covers all regions.
  • Deny rules. Azure NSGs and Google firewall rules can deny. AWS security groups can only allow; denies go in network ACLs or AWS Network Firewall.
  • Default redundancy. S3 and regional Cloud Storage are multi-zone by default. An Azure LRS account is one datacentre. Compare prices like for like.
  • Archive is not the same tier. Azure Archive must be rehydrated (hours). Google Cloud Archive reads in milliseconds. Glacier depends on the class.
  • Region pairs. Azure picks the GRS target for you. On AWS and Google Cloud you choose the DR region and turn replication on yourself.
  • Resource groups are Azure-only. Every resource needs one, and deleting the group deletes everything in it.
  • Identity is the hardest part to translate. Entra ID is a directory; AWS IAM is per account; Google Cloud uses Google identities. Decide early which directory is the source of truth for all clouds.
  • Licensing changes the cost case. Azure Hybrid Benefit works on shared hosts; Windows Server licences you bring to AWS or Google Cloud generally need dedicated hardware.
  • Same name, different product. AWS's Application Load Balancer is Azure's Application Gateway; AWS's security group is closer to an Azure NSG plus ASG.
