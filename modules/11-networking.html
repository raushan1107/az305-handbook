Networking is where cloud designs quietly fail. The app is perfect, the database is zone-redundant, and then: the address range overlaps with the head office, the database is reachable from the internet, or every store's traffic hairpins through one VPN that can't take the load. This module gives you the network plan an architect draws before anyone deploys a VM.

11.0

The mental map

Think of an Azure network as a city. Virtual networks are gated colonies with their own streets (subnets). Peering and a central hub are the ring road. VPN and ExpressRoute are the highway to your old office. Private endpoints bring PaaS services inside the colony walls. At the city gates, Front Door, Application Gateway and Azure Firewall decide who gets in and where they go.

11.1

Why the network is designed first

Imagine this

Building a township. You can repaint houses and change shops any time. But once the roads, plot numbers and water pipes are laid, changing them means digging up every street. In Azure, address spaces, topology and hybrid links are the roads and pipes. They're cheap to plan and painful to change.

Developer view

"I'll create a VNet with the default 10.0.0.0/16 and put everything in it. We can sort out the network later."

Architect view

"Every team picks 10.0.0.0/16 and then nobody can peer or connect to on-premises. We start with an IP address plan for the whole company, a hub for shared services, and private by default for PaaS. The network team owns the roads; app teams own their colonies."

Mindset takeaway

Three network decisions are close to one-way doors (Module 01): the address plan, the topology (hub-spoke or Virtual WAN), and the hybrid link. Take them early, together, and write them down.

11.2

Virtual networks and address planning

Your private colony in Azure

Definition

An Azure Virtual Network (VNet) is a logically isolated private network in one region and one subscription, defined by one or more address spaces (CIDR ranges) and divided into subnets. Resources in a VNet communicate privately with each other by default and can be connected to other VNets (peering) and to on-premises networks (VPN, ExpressRoute).

In plain words

A VNet is a gated colony; subnets are its lanes. Houses in the colony can visit each other freely. Visitors from outside need a gate (public IP, load balancer, gateway). A VNet lives in one region; you need one per region.

Facts worth remembering

  • Azure reserves 5 addresses in every subnet (first four and the last). A /29 gives you only 3 usable.
  • Some services need a dedicated subnet with a fixed name: GatewaySubnet (VPN/ExpressRoute, /27 or larger), AzureFirewallSubnet (/26), AzureBastionSubnet (/26 or larger). Others need a delegated subnet (App Service VNet integration, Container Apps, SQL MI).
  • Address spaces must not overlap with peered VNets or on-premises ranges you connect to. This is the most expensive mistake to fix later.
  • Plan for growth: a /16 per region hub-and-spokes, carved into /22–/24 spokes, leaves room for years.
  • Outbound internet: since 31 March 2026, new virtual networks use private subnets by default, with no implicit internet access (the old default outbound access). Plan explicit egress with NAT Gateway, a firewall or Load Balancer outbound rules.
Common trap

Two VNets built with 10.0.0.0/16 by different teams can never be peered. Re-addressing a live VNet means moving every resource. An enterprise IP address management (IPAM) plan, such as Azure Virtual Network Manager's IPAM pools, prevents it on day one.

Exam cue

"How many subnets / addresses are available?" → remember the 5 reserved. "Connect two VNets that overlap" → not possible with peering; re-address (or NAT through an appliance). "Outbound internet with a fixed public IP for many VMs" → NAT Gateway.

11.3

Filtering traffic: NSGs and ASGs

The guard at each lane

Definition

A network security group (NSG) contains prioritised allow and deny rules that filter inbound and outbound traffic by source, destination, port and protocol (layer 3–4). It can be associated with a subnet or a network interface. An application security group (ASG) groups VMs by role (for example "web" or "db") so NSG rules can refer to the group instead of IP addresses.

In plain words

NSGs are guards with a list: "Port 443 from the internet to web servers: allow. Port 1433 from web servers to database servers: allow. Everything else: deny." Rules are checked by priority number, lowest first, and the first match wins. ASGs let you write "web" instead of "10.1.2.4, 10.1.2.5, 10.1.2.9…".

  • Every NSG has default rules: allow VNet-to-VNet, allow from Azure Load Balancer, deny all other inbound; allow outbound to the internet.
  • Service tags (Internet, VirtualNetwork, Storage.CentralIndia, AzureLoadBalancer) stand for Microsoft-maintained IP ranges.
  • Effective security rules and IP flow verify (Network Watcher) show why a packet was allowed or denied.
  • NSG flow logs can't be created any more (since June 2025) and retire on 30 September 2027. Use VNet flow logs, which cover a whole VNet; send them to Log Analytics with Traffic Analytics (Module 04).
Exam cue

"Allow or deny traffic by IP, port, protocol between subnets" → NSG. "Group VMs by role so rules don't use IPs" → ASG. "Filter by FQDN, threat intelligence, central rules for many VNets" → Azure Firewall (not an NSG). "Why is my traffic blocked?" → IP flow verify / effective rules.

11.4

Topology: hub and spoke, Virtual WAN

The ring road and the colonies

Definition

VNet peering connects two VNets (same or different regions) over the Microsoft backbone with low latency. Peering is not transitive: A↔B and B↔C does not give A↔C.

In a hub-and-spoke topology, a central hub VNet hosts shared services (firewall, gateways, Bastion, DNS) and is peered with workload spoke VNets; user-defined routes (route tables you write) send traffic through the hub's firewall.

Azure Virtual WAN is a Microsoft-managed networking service whose hubs come with built-in routing, VPN, ExpressRoute and optional Azure Firewall ("secured hubs"), giving any-to-any connectivity across hubs.

In plain words

Peering is a private road between two colonies. If A is peered to the hub and B is peered to the hub, A still can't reach B directly: roads don't chain. So spoke-to-spoke traffic goes through the hub's firewall, by a route you set. Virtual WAN is the same idea, but Microsoft builds and runs the ring road, its junctions and toll gates for you.

Hub and spokeVirtual WAN
Who builds the hubYou (a VNet with gateways, firewall, UDRs)Microsoft (a managed hub resource)
Transit between spokesThrough a firewall or NVA with UDRsBuilt in (any-to-any), optionally via secured hub
Branch sitesTens of site-to-site tunnels per gatewayHundreds to thousands of sites, SD-WAN partner integration

Good practice: Azure Virtual Network Manager

Azure Virtual Network Manager creates hub-and-spoke or mesh connectivity across many VNets and subscriptions from one place, and applies security admin rules that override NSGs (for example "always deny RDP from the internet"). It's governance for the network layer.

Exam cue

"Connect two VNets with low latency over the backbone" → peering. "Spoke A must reach spoke B" → route through the hub firewall/NVA (peering isn't transitive) or use Virtual WAN. "Hundreds of branch offices", "global transit", "SD-WAN", "minimise network management" → Virtual WAN. "Centrally manage connectivity and security admin rules across subscriptions" → Virtual Network Manager.

Say: “A private road between two colonies, built from both ends.”

11.5

Hybrid connectivity: VPN and ExpressRoute

The highway to your datacentre

VPN Gateway

An encrypted IPsec tunnel over the public internet. Site-to-site links an office or datacentre; point-to-site links individual laptops; VNet-to-VNet links VNets. Quick to set up, cheap, bandwidth up to about 10 Gbps depending on the gateway SKU, latency as good as the internet that day.

ExpressRoute

A private connection through a connectivity provider (or directly at a peering location with ExpressRoute Direct) into Microsoft's network. Does not traverse the internet. Predictable latency, bandwidth from 50 Mbps to 10 Gbps per circuit (100 Gbps with Direct), built-in redundancy (two connections), financially backed SLA.

Imagine this

VPN is an armoured van on the public highway: your goods are locked and safe, but you're in the same traffic as everyone else. ExpressRoute is a private freight railway line from your warehouse to Microsoft's: costlier and takes weeks to lay, but no traffic jams, and it never touches the public road.

ExpressRoute details the exam likes

Private peeringReach your VNets' private IPs. The normal use.
Microsoft peeringReach Microsoft 365 and Azure public endpoints over the private circuit.
Circuit SKUsLocal (only regions near the peering location, no egress data charge), Standard (regions in the same geopolitical area), Premium (all regions worldwide, more routes and VNet links).
Global ReachConnects two of your on-premises sites to each other through Microsoft's backbone, using their ExpressRoute circuits.
FastPathSends traffic straight to VMs, bypassing the gateway, for the lowest latency at high throughput.
ExpressRoute DirectConnect your own routers at 10 or 100 Gbps directly at a Microsoft peering location; physical isolation for regulated industries.
Common trap

"ExpressRoute is encrypted." It's private, not encrypted. If a regulator says "encrypted in transit", add MACsec (ExpressRoute Direct) or run IPsec over ExpressRoute (VPN over the private peering), or rely on TLS at the application layer.

Exam cue

"Encrypted over the internet", "quick and cheap", "remote users" (point-to-site) → VPN Gateway. "Private, does not traverse the internet", "predictable latency", "high bandwidth", "SLA" → ExpressRoute. "Reach regions in another geography" → ExpressRoute Premium. "Connect two datacentres through Microsoft" → Global Reach. "Failover if ExpressRoute fails" → site-to-site VPN as backup.

Say: “An armoured van on the public highway, or a private railway line. These forms are where you choose.”

11.6

Private access to PaaS, and DNS

Bringing services inside the colony walls

PaaS services like Azure SQL, Storage and Key Vault have public endpoints by default. Two features let your VNet reach them privately, and they're constantly confused.

Service endpoint

Your subnet reaches the service's public endpoint over the Azure backbone, and the service's firewall can say "allow only this subnet". The service still has a public IP. Free, simple, works only from Azure VNets (not on-premises).

Private endpoint (Private Link)

A network interface with a private IP from your subnet that maps to one specific resource (this storage account, this database). Reachable from peered VNets and on-premises over VPN/ExpressRoute; the public endpoint can be disabled entirely. Charged per hour and per GB.

Imagine this

A service endpoint is a VIP lane on the public road to the bank: faster, and the bank only lets cars from your colony in, but it's still the bank's public building. A private endpoint is the bank opening a branch inside your colony, with a house number on your street. Nobody outside even sees it.

  • Keep private DNS zones centrally (in the Connectivity subscription), linked to every VNet, and use Azure Policy to register each new private endpoint automatically.
  • Azure DNS Private Resolver lets on-premises DNS servers resolve Azure private zones (inbound endpoint) and Azure resolve on-premises names (outbound endpoint), without DNS VMs.
  • Private Link service is the other direction: publish your own service (behind a Standard Load Balancer) privately to other customers' VNets.
Exam cue

"Access PaaS from on-premises privately", "private IP for the service", "disable public access", "data exfiltration protection (one specific resource)" → private endpoint. "Restrict a service to a subnet, no extra cost" → service endpoint. "On-premises must resolve Azure private names" → DNS Private Resolver. "Offer your service privately to other tenants" → Private Link service.

Say: “The bank opened a branch inside your colony, and closed its door on the main road.”

Four services, two questions. Is the traffic HTTP(S)? (layer 7 or layer 4) and Is it global or regional? Answer both and there's only one box left.

11.8

Protecting the edge

The last layer of the network design is the guards: what inspects traffic, what absorbs attacks, how admins get in, and how servers get out.

Azure Firewall

Definition

Azure Firewall is a cloud-native, stateful network firewall as a service with built-in high availability and autoscaling. It filters east-west and north-south traffic with network rules, application rules (FQDNs) and DNAT rules, uses Microsoft threat intelligence, and is managed through Firewall Policy. SKUs: Basic (small businesses), Standard, and Premium (adds TLS inspection, IDPS, URL filtering and web categories).

In plain words

NSGs are guards at each lane checking IDs. The firewall is the central checkpost on the ring road: it knows domain names ("allow *.ubuntu.com, deny everything else"), recognises known bad addresses, and with Premium can open and inspect parcels (TLS inspection). It logs everything centrally.

Developer view

"I'll open port 3389 to my home IP so I can RDP into the VM."

Architect view

"No management ports on the internet, ever. Admins come through Bastion with Entra sign-in and PIM (Module 03), or just-in-time access from Defender for Cloud. One open RDP port is the most common way in for ransomware."

Exam cue

"Central filtering of outbound traffic by FQDN", "threat intelligence", "inspect traffic between spokes" → Azure Firewall (Premium for "TLS inspection" or "IDPS"). "Protect against SQL injection / XSS" → WAF on Front Door or Application Gateway. "RDP/SSH without public IPs" → Bastion. "Mitigate DDoS with telemetry and cost protection" → DDoS Network Protection.

Mindset takeaway

Defence in depth, drawn as layers: edge (Front Door + WAF, DDoS), perimeter (Azure Firewall in the hub), segment (NSGs per subnet), service (private endpoints, public access off), identity (Part I). An attacker should have to beat every layer, not just one.

11.10

Recap and self-check

Architect's network checklist

  • An organisation-wide, non-overlapping IP address plan, with room to grow.
  • A topology chosen: hub-and-spoke, or Virtual WAN for many branches and regions.
  • Hybrid link sized and made redundant: ExpressRoute with VPN backup, or VPN alone where enough.
  • PaaS reached through private endpoints, public access disabled, DNS designed centrally.
  • Load balancer picked by protocol and scope; Front Door for global web, App Gateway for regional.
  • Layers of protection: WAF and DDoS at the edge, firewall in the hub, NSGs per subnet.
  • No management ports on the internet; Bastion or JIT for admins; explicit egress via NAT or firewall.
  • Flow logs and firewall logs in Log Analytics, with Traffic Analytics (Module 04).

Self-check

1. Spoke A and spoke B are each peered to a hub. VMs in A can't reach VMs in B. Why, and what do you do?

VNet peering is not transitive. Route spoke-to-spoke traffic through a firewall or NVA in the hub with user-defined routes (or peer A and B directly, or use Virtual WAN).

2. A company needs a private, high-bandwidth connection to Azure that does not traverse the internet, with predictable latency. What do you recommend, and what's a sensible backup?

ExpressRoute, with a site-to-site VPN as a failover path.

3. On-premises servers must reach an Azure SQL Database over ExpressRoute using a private IP, and the database's public access must be disabled. What do you configure?

A private endpoint for the SQL server, a private DNS zone (privatelink.database.windows.net), and DNS Private Resolver (or forwarders) so on-premises DNS resolves the private IP. A service endpoint wouldn't work from on-premises.

4. A web app runs in two regions for global users. You need TLS at the edge, caching of static content, WAF and automatic failover between regions. Which service?

Azure Front Door (Standard or Premium) with a WAF policy.

5. In one region, requests to /images/* must go to one pool of servers and /api/* to another, with SQL injection protection. Which service?

Application Gateway v2 with path-based routing and WAF.

6. Admins need RDP to Windows VMs without public IPs on the VMs and without a VPN client. What do you deploy?

Azure Bastion in the VNet (or the hub, reaching peered spokes).

Carry this into Module 12

A migration is mostly a network event: replication traffic needs bandwidth (ExpressRoute), migrated servers need address space that doesn't clash (the IP plan), and cut-over means changing DNS and routes. With the roads in place, it's time to move the city.
