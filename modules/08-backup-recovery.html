08.0

The mental map

Every continuity design answers three questions, at three different scales. Stay up when a server or a datacentre fails (high availability). Come back when a whole region fails (disaster recovery). Go back in time when data itself is damaged, deleted or encrypted (backup). Two numbers, RTO and RPO, decide how much you spend on each.

08.1

HA, DR and backup are three different jobs

Imagine this

A hospital. High availability is the generator that kicks in the moment the power goes: patients barely notice. Disaster recovery is the agreement with another hospital across town: if this building floods, ambulances move patients there, and it takes hours. Backup is the medical records room: if a file is wrongly edited or a virus scrambles the computers, you pull last week's paper copy. A hospital needs all three, and none of them replaces the others.

The two numbers that decide everything

High availabilityDisaster recoveryBackup
Protects againstServer, rack, datacentre (zone) failureLoss of a whole regionDeletion, corruption, ransomware, bad deployments
Typical RTOSeconds, automaticMinutes to hoursHours (depends on size)
Typical RPOZero (synchronous copies)Seconds to minutes (asynchronous)Hours to a day (last backup)
Azure toolsSets, zones, ZRS, zone-redundant PaaSSite Recovery, geo-replication, failover groups, GRSAzure Backup, PITR, soft delete, versioning
Copies the damage?Yes, instantlyYes, within secondsNo: older copies stay clean
Common trap

"We have geo-replication, so we don't need backup." Replication copies a DROP TABLE or a ransomware encryption to the other region within seconds. Replication protects against losing a place; only backup protects against losing the data's integrity.

Developer view

"Backup is ticked on in the portal. We're covered."

Architect view

"Each workload has an agreed RTO and RPO signed by the business owner. Checkout gets zones and a warm secondary region; the HR portal gets a nightly backup. And every quarter we prove a restore and a failover, with a stopwatch."

Exam cue

"Minimise data loss" → think RPO (replication frequency). "Minimise downtime" → think RTO (failover speed). "Recover from accidental deletion" or "ransomware" → backup, never replication alone. "Survive a datacentre failure" → availability zones. "Survive a regional outage" → a second region.

08.2

High availability building blocks

Racks, buildings and cities

Definition

An availability set spreads VMs across fault domains (separate power and network) and update domains (separate maintenance windows) inside one datacentre. An availability zone is a physically separate datacentre, or group of datacentres, within an Azure region, with independent power, cooling and networking. A region pair is two regions in the same geography that Azure links for platform recovery, sequential updates and geo-redundant storage.

In plain words

Three sizes of "don't put all your eggs in one basket". A set spreads your VMs across racks in one building. Zones spread them across buildings a few kilometres apart. A second region puts them in another city. Each step survives a bigger failure, and adds a little latency and cost.

Facts worth remembering

  • VM SLAs: single VM with Premium SSD, Premium SSD v2 or Ultra disks: 99.9%. Two or more in an availability set: 99.95%. Two or more across zones: 99.99%.
  • An availability set gives up to 3 fault domains and up to 20 update domains. A VM joins a set or a zone only at creation.
  • Services are zonal (pinned to one zone you pick, like a VM or disk) or zone-redundant (spread for you, like ZRS storage, zone-redundant SQL Database or App Service). Not every region has zones; Central India and South India do, and so does Germany West Central.
  • Region pairs (for example Central India ↔ South India) get staggered platform updates and are the GRS target. Newer regions may have no pair; then you choose the secondary yourself.
  • Virtual Machine Scale Sets (Module 09) with flexible orchestration spread instances across zones and fault domains automatically.
Name check

"Zone-redundant" and "zonal" are not the same thing. A zonal VM sits in exactly one zone: if that zone fails, it fails. You get zone resilience only by running several zonal instances across zones behind a load balancer, or by using a zone-redundant service.

Exam cue

"Protect against datacentre failure", "99.99% for VMs" → availability zones. "Protect against hardware or rack failure and planned maintenance", "region has no zones" → availability set. "Protect against regional failure" → deploy to a second region (paired where possible).

08.3

Azure Backup and its vaults

One service, two kinds of vault

Definition

Azure Backup is a managed, agent-optional backup service that protects Azure VMs, disks, file shares, blobs, databases in VMs, Kubernetes clusters and on-premises machines. Backups are stored in a vault, governed by backup policies (schedule and retention), encrypted at rest, and isolated from the protected resource's own credentials.

In plain words

You don't run backup servers or buy tapes. You create a vault, write a policy ("every night at 11 p.m., keep 30 dailies, 12 monthlies, 7 yearlies"), and point it at your resources. Azure takes the snapshots, moves the copies into the vault, and expires them on schedule. You pay per protected instance plus the storage used.

Imagine this

A bank locker. Your jewellery at home is the live data. The locker is in another building, has its own key, and the bank keeps a register of when you put things in. Even if a thief gets into your house, the locker copy is safe. The two vault types are like two lockers at the same bank, built for different-shaped items.

VaultProtectsNotes
Recovery Services vaultAzure VMs · SQL Server and SAP HANA in Azure VMs · Azure Files · on-premises files and folders (MARS agent) · on-premises workloads via MABS or DPMThe original vault. Also the home of Azure Site Recovery replication.
Backup vaultAzure Blobs · Azure Disks · Azure Database for PostgreSQL (flexible server) · AKS clusters · newer workloadsThe newer vault type. New datasources tend to arrive here first.

Facts worth remembering

  • Vault storage redundancy (LRS, ZRS or GRS) must be chosen before the first item is protected. Turn on Cross Region Restore on a GRS vault to restore in the paired region whenever you choose, not only when Microsoft declares a disaster.
  • The vault must be in the same region as the resources it protects. Multi-region estate = one vault per region.
  • VM policies: Standard (once a day) or Enhanced (several times a day, down to every 4 hours, longer snapshot retention, and required for Trusted Launch VMs).
  • For SQL Server in a VM, Azure Backup takes full, differential and log backups every 15 minutes: point-in-time restore inside a VM.
  • Blobs have two modes: operational backup (continuous, stays in the storage account, uses point-in-time restore) and vaulted backup (copies into the Backup vault, survives the account being deleted).
  • Azure Policy can enforce "every VM tagged Environment=Prod is backed up" with a DeployIfNotExists policy (Module 02).
Name check

Backup center has been folded into Azure Business Continuity Center: one place to see what is protected (by Backup and Site Recovery), what isn't, which jobs failed and which security settings are missing. On-premises protection still uses the MARS agent (files and folders) or Microsoft Azure Backup Server (MABS) for application-aware backups.

Developer view

"I'll write a script that copies the database file to a storage account every night."

Architect view

"Scripts fail silently. A vault gives us policy-driven retention, alerts on failed jobs, separate credentials from production, soft delete and immutability, and one report the auditors can read. And Policy makes sure nobody forgets to enable it."

Exam cue

"Back up Azure VMs, Azure Files, SQL Server in a VM" → Recovery Services vault. "Back up blobs, managed disks, PostgreSQL, AKS" → Backup vault. "Back up on-premises files and folders without a server" → MARS agent. "Restore to the secondary region on demand" → GRS vault with Cross Region Restore.

08.4

Backups that survive ransomware

Assume the attacker has admin rights

Modern ransomware doesn't just encrypt servers. It first finds the backups and deletes them, using a stolen admin account. So the real design question is: can someone with Contributor or Owner rights destroy our backups? Azure Backup has four layers that answer "no".

Soft deleteDeleted backup data is kept for 14 days by default, and can be extended with enhanced soft delete. Set it to always on so it can't be switched off.
Immutable vaultRecovery points can't be deleted or shortened before they expire. Once the setting is locked, nobody (not even Microsoft support for you) can turn it off.
Multi-user authorisation (MUA)Critical operations (disable soft delete, reduce retention, stop protection) need approval through a Resource Guard owned by a different team, ideally in a different subscription or tenant.
Encryption and private accessData is encrypted at rest (customer-managed keys optional), backup traffic can use private endpoints, and vault access follows Azure RBAC roles like Backup Operator.
Common trap

Locking immutability is irreversible. Turn it on unlocked first, check that your retention policies are what you really want (an accidental 10-year retention is now a 10-year bill), and only then lock it.

Exam cue

"Prevent malicious deletion of backups", "ransomware" → soft delete (always-on) + immutable vault. "Require a second person's approval for critical backup operations" → multi-user authorisation with a Resource Guard.

Mindset takeaway

Design backups with the attacker in mind, not just the failed disk. The question isn't "do we have a backup?" but "who can delete it, and how would we know?"

Portal demoHarden the vault: always-on soft delete, immutability and a Resource Guard~4 min

Goal: Make the vault survive an attacker with admin rights, and see why locking is a one-way door.

  1. Vault › Properties › Security settings › Update: show soft delete retention and the Enable always-on soft delete option. Don't enable always-on on a demo vault (you couldn't clean up quickly).
  2. Vault › Properties › Immutable vault › Settings: tick Enable vault immutability, leave it unlocked. Point at the lock option and its warning. Save unlocked or cancel.
  3. Search Resource Guards › + Create: show that it's a separate resource, normally in the security team's subscription, and the list of protected operations. Create it in the demo RG if you have time.
  4. Vault › Properties › Multi-user authorization › Update: associate the Resource Guard. Then try to reduce soft delete retention: the portal asks for authorisation from the guard.

Point out while you are there

  • Locked immutability can never be undone. That's the point, and also the trap.

Say: “Two keys to open the locker: one with the backup team, one with security.”

Clean up: Remove the MUA association and delete the Resource Guard before deleting the vault.

In plain words

For PaaS databases the question is rarely "how do we back it up?" and almost always "is the default retention long enough?" Seven days of PITR is fine for a fat-finger mistake; it's useless for an auditor asking about March three years ago. That's what long-term retention is for.

Exam cue

"Keep Azure SQL backups for 7 years" → long-term retention (LTR). "Restore Cosmos DB to any second in the last 30 days" → continuous backup. "Back up managed disks with minimal impact" → Azure Disk Backup (incremental snapshots, Backup vault).

08.6

Azure Site Recovery

A spare building, ready in minutes

Definition

Azure Site Recovery (ASR) is a disaster recovery service that continuously replicates workloads running on physical servers, VMware and Hyper-V VMs, and Azure VMs from a primary site to a secondary location. When an outage occurs you fail over to the secondary, and fail back when the primary is restored. Recovery plans orchestrate the order, scripts and manual steps of a failover.

In plain words

ASR keeps a copy of your VMs' disks in another region, updated every few minutes. Until you need it, there are no running VMs on the other side, only disks, so it's much cheaper than running a second copy. On the bad day, one click (or one recovery plan) creates the VMs from the latest recovery point.

Facts worth remembering

  • Azure-to-Azure: crash-consistent recovery points every few minutes; app-consistent points on a schedule you set (hours). RPO is typically measured in minutes, not seconds.
  • Scenarios: Azure → Azure (region to region, or zone to zone in the same region), VMware / physical → Azure, Hyper-V → Azure. ASR is also how many teams first rehearse a migration (Module 12).
  • Test failover into an isolated VNet costs only the test VMs' running time. Do it after every major change, and at least twice a year.
  • Billing is per protected instance (the first 31 days of each instance are free) plus storage in the target region.
  • ASR replicates VMs. PaaS services use their own geo features: SQL failover groups, Cosmos DB multi-region, GRS storage, Front Door for traffic.
Common trap

The VMs fail over perfectly, and nothing works: the target region has no capacity reserved, the IP addresses changed, DNS still points at the dead region, or the domain controller was never replicated. Plan the network, DNS and identity on the DR side, and consider capacity reservations for critical sizes.

Developer view

"DR means a second copy of everything running in another region."

Architect view

"For most VMs, a running copy is money burnt for a day that may never come. ASR gives an RTO of tens of minutes at a fraction of the cost. We pay for a hot copy only where the RTO is seconds."

Exam cue

"Replicate VMs to another region", "orchestrated failover", "recovery plan", "test DR without affecting production" → Azure Site Recovery. "Minimise cost of DR for VMs" → ASR (no running VMs at the target). "Fail over on-premises VMware VMs to Azure" → ASR (VMware to Azure).

08.7

Disaster recovery patterns

Every DR design sits somewhere on one dial: how much you keep running in the second region before disaster strikes. Turn the dial up and RTO falls, and the bill rises.

The pieces of a regional failover

  1. Traffic: a global entry point that can move users (Front Door or Traffic Manager, Module 11).
  2. Compute: already running (active), scaled down (warm), or created by ASR or IaC (pilot light, backup).
  3. Data: geo-replicated with a known RPO: SQL failover groups, Cosmos DB multi-region, GZRS storage.
  4. Dependencies: identity, DNS, Key Vault, secrets and messaging must exist in the secondary too.
  5. Decision and drill: who declares the disaster, the runbook, and a test date in the calendar.
Exam cue

"Minimise cost, RTO of a day is acceptable" → backup and restore (GRS vault, Cross Region Restore). "RTO of minutes, cost matters" → warm standby. "No downtime during a regional outage", "users in both regions" → active-active behind Front Door.

Mindset takeaway

Resilience is a budget conversation. Show the business owner the dial, the RTO at each position and the monthly cost. Let them choose with their eyes open, then write the answer down.

08.9

Recap and self-check

Architect's continuity checklist

  • RTO and RPO agreed per workload with the business owner, and written down.
  • HA, DR and backup treated as three separate layers, each sized to the numbers.
  • Availability zones (or sets where zones don't exist) for anything Tier 1 or Tier 2.
  • A DR pattern chosen per workload, with traffic, compute, data and dependencies covered.
  • Vaults per region, redundancy set before the first backup, Cross Region Restore where needed.
  • Soft delete always on, immutability locked, MUA with a Resource Guard owned by another team.
  • Default PaaS retention checked; LTR or continuous backup added where audits need it.
  • Restores and failovers tested on a calendar, with a stopwatch.

Self-check

1. An application uses two VMs and must stay available if a single Azure datacentre fails. The region supports zones. What do you use, and what SLA do you get?

Place the VMs in different availability zones behind a zone-redundant load balancer: 99.99%. An availability set only protects against rack-level failures inside one datacentre (99.95%).

2. A company replicates its database to a second region with a 5-second lag. Is a backup still needed?

Yes. Replication copies deletions, corruption and ransomware encryption within seconds. Only backups give a clean copy from before the damage.

3. You must back up Azure Blob data and managed disks. Which vault type?

A Backup vault. Azure VMs, Azure Files and SQL in VMs use a Recovery Services vault.

4. A security officer wants any attempt to disable soft delete or reduce backup retention to need approval from the security team. What do you configure?

Multi-user authorisation using a Resource Guard in a subscription the security team owns (ideally with PIM for the approval role). Add an immutable vault to stop recovery points being deleted early.

5. Forty application VMs must be recoverable in another region within two hours, at the lowest cost, with the database tier started before the web tier. What do you recommend?

Azure Site Recovery (Azure to Azure) with a recovery plan that groups the database VMs first, then app, then web. No VMs run in the target until failover.

6. Azure SQL Database backups must be kept for 7 years for auditors. What do you configure?

Long-term retention (LTR) with a yearly backup kept for 7 years. Point-in-time restore only covers up to 35 days.

Carry this into Module 09

Every compute choice comes with a different continuity story. A VM needs you to add backup and ASR; App Service and Functions bring zone redundancy with a setting; containers need their images and state protected separately. As you choose where code runs, keep asking: how does this come back on the bad day?
